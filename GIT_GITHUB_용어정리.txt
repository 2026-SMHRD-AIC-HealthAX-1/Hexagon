Git / GitHub 용어 정리
(작성일: 2026-09-11)

이 프로젝트(Eye-God)에서 실제로 쓰고 있는 워크플로우 기준으로 정리한
용어 설명입니다. 팀원과 공유해서 같이 참고하면 됩니다.

===========================================
1. 기본 단위
===========================================

- Repository (저장소, 줄여서 repo)
  프로젝트 전체를 담는 그릇. 지금의 Eye-God 저장소
  (https://github.com/StarBlossom99/Eye-God)가 그 예.

- Commit
  "이 시점의 코드 상태"를 하나의 스냅샷으로 저장하는 것.
  명령어: git commit

- Branch (브랜치)
  코드의 독립된 작업 줄기. main도 그냥 브랜치 하나일 뿐이며, git 자체가
  main을 특별 취급하는 게 아니라 "여기가 신뢰할 수 있는 기준 코드"라고
  팀이 정한 관례일 뿐이다. 팀원이 "철수-design"처럼 자기 이름 브랜치를
  파서 거기서 작업하면 서로의 작업이 섞이지 않는다.

===========================================
2. 서버와 주고받기
===========================================

- Push
  로컬 커밋을 원격 저장소(GitHub)에 올리는 것.
  명령어: git push

- Pull
  원격 저장소의 최신 내용을 로컬로 받아오는 것 (사실상 fetch + merge를
  한 번에 하는 것).
  명령어: git pull

- Clone
  원격 저장소 전체를 처음으로 "내 컴퓨터"에 복사해오는 것.
  명령어: git clone <저장소 주소>

- Fork
  남의 저장소를 "내 GitHub 계정 안에" 통째로 복사하는 것. clone과
  다른 점: clone은 "내 컴퓨터로", fork는 "내 GitHub 계정의 새 저장소로"
  복사한다는 점. 이 프로젝트의 팀원 기여 워크플로우가 이 방식을 쓴다
  (WINDOWS_TEST_GUIDE.txt 1번, 3번 참고).

- Remote
  로컬 저장소가 기억하는 "원격 주소들". 보통 내 fork를 origin, 원본
  저장소를 upstream이라는 이름으로 구분해서 등록한다.
  명령어: git remote add upstream <원본 저장소 주소>

===========================================
3. 변경사항 합치기
===========================================

- Merge
  한 브랜치의 변경사항을 다른 브랜치(보통 main)에 합치는 것.

- Pull Request (PR)
  "제 fork/브랜치의 이 변경사항을 main에 merge해주세요"라는 요청.
  코드 diff를 보여주고, 코멘트를 달고, 승인(Approve)하는 과정이 이 PR
  화면 안에서 이루어진다. 이름은 "Pull 요청"이지만 실제로는 "내 것을
  당겨가서(merge해서) 반영해달라"는 의미에 가깝다.

- Review / Approve
  다른 사람이 PR의 코드를 검토하고 "이대로 merge해도 된다"고 승인하는
  것.

- Merge conflict (충돌)
  두 브랜치가 같은 파일의 같은 부분을 서로 다르게 고쳐서, git이 자동
  으로 합치지 못하는 상황. 사람이 직접 어느 쪽을 남길지 골라줘야 한다.

===========================================
4. 이 프로젝트의 실제 흐름
===========================================

팀원 기준:
1) Fork      - 원본 저장소를 내 계정에 복사
2) Clone     - 내 fork를 내 컴퓨터로 복사
3) Branch    - 작업용 브랜치 생성 (git checkout -b 본인이름-design)
4) Commit    - 작업 내용 저장
5) Push      - 내 fork(origin)에 올림
6) Pull Request - 원본 저장소의 main에 합쳐달라고 요청

관리자(StarBlossom99) 기준:
7) Review/Approve - PR 내용 검토, 필요하면 로컬로 받아서 직접 실행/테스트
8) Merge          - 문제없으면 실제 main에 반영

팀원은 원본 저장소에 push 권한이 없으므로, 6번까지만 할 수 있고 7~8번은
관리자만 할 수 있다 (의도된 구조 - 자세한 배경은 WINDOWS_TEST_GUIDE.txt
1번 참고).
