리듬게임 비주얼 개선 (lab 버전) — 작업 기록 및 적용 가이드
============================================================
(작성일: 2026-09-14)

현재 상태: 구현 완료, 디자인 테마 사용자 확인 완료("테마 자체는 괜찮다").
           아직 원본을 교체하지는 않은 대기 상태 — 원할 때 아래 5번 절차로 적용.

* 원본(rhythm_game.html / js/rhythm_game.js / 백엔드 전체)은 한 줄도 수정되지
  않았다. 신규 파일 3개만 추가된 상태라 지금 당장 되돌릴 것도 없다.


1. 작업 지시 내용 (사용자 원문 규칙)
------------------------------------
1. 게임 메커니즘(시선 각도 변경으로 좌측/중앙/우측 선택 및 눈 깜빡임으로 블록
   히트 등)은 변경없이 그대로 유지
2. 개발 범위는 시각적 효과와 디자인으로 한정 (블록을 맞출때 이펙트 효과, 블록
   디자인, 게임의 배경 등등)
3. 소리는 개발 내용에 포함되지 않는다.
4. 원본 코드에 영향을 미치지 않도록 별도의 환경에서 개발하되, 언제든 원본을
   대신할 수 있도록 호환성을 신경써야한다.
5. 실제 게임과 최대한 유사하게 구현한다.
6. 진행 도중 중요한 의사결정은 사용자에게 동의를 구한다.

참고 자료: reference_img/1~5.jpeg (실제 리듬게임 스크린샷 5장)


2. 구현 전 확인한 선택 사항 (AskUserQuestion 답변)
------------------------------------------------
- 레인 렌더링 방식: "3D 원근 하이웨이" 선택
  (레퍼런스 5장 전부 소실점 원근 방식이라 체감 차이가 가장 큼. 평면 유지 +
   이펙트만 강화하는 안은 기각)
- 비주얼 톤: "네온 우주" 선택 (레퍼런스 1·4번 — 검은 우주 배경 + 마젠타/시안
  네온 레인 + 별). 블루 테크(2·5번), 골드 클래식(3번)은 기각.


3. 핵심 설계 판단 — 백엔드를 건드리지 않아도 되는 이유
-----------------------------------------------------
서버(rhythm_game_session.py)가 프레임마다 보내주는 상태 payload 안에 이미
고급 비주얼에 필요한 정보가 전부 들어있다:

    {
      type, paused, focus_lane,
      notes: [{ id, lane, progress(0~1.3), result(null|perfect|miss) }],
      score, perfect_count, miss_count,
      last_judgment: null | { lane, result },
      remaining, finished
    }

따라서 "서버가 보내주는 상태를 화면에 어떻게 그리는가"만 새로 짜면 되고,
백엔드/WebSocket/판정 로직은 원본 그대로 재사용한다. lab 버전도 원본과
똑같이 /ws/rhythm-game 에 접속한다 → 규칙 1(메커니즘 무변경)이 코드 구조상
자동으로 보장된다.

콤보 수치는 서버가 주지 않으므로 last_judgment 이벤트를 프론트에서 세서
만든다 (perfect면 +1, miss면 0으로 리셋). 순수 표시용이라 점수 계산과는 무관.


4. 새로 만든 파일 (전부 신규, 원본 수정 0건)
--------------------------------------------
- web/frontend/rhythm_game_lab.html      테스트 페이지. DOM id는 원본과 동일하게 유지
- web/frontend/js/rhythm_game_lab.js     새 렌더러 (실제 작업의 대부분)
- web/frontend/css/rhythm_game_lab.css   네온 테마. 이 페이지에서만 link 하므로
                                         다른 화면에는 영향 없음

구현한 시각 효과:
- 소실점으로 모이는 3D 원근 하이웨이 (노트가 멀리선 작고 가까울수록 커짐)
- 네온 레일(바깥 마젠타 / 안쪽 바이올렛) + 앞으로 흘러오는 원근 그리드
- 포커스 중인 레인을 밝은 반투명 기둥으로 표시 (레인 전환 시 부드럽게 이동)
- 판정선 + 레인별 발광 패드(포커스 레인은 맥동)
- 히트 시: 파티클 버스트 / 충격파 링 / 레인 광선 빔 / 화면 흔들림
- Miss 시: 붉은 파티클 + 화면 가장자리 붉은 비네트
- 중앙 콤보 카운터 + 판정 텍스트(PERFECT / MISS) 스케일 애니메이션
- 좌측 정확도 게이지, 상단 시간 게이지, SCORE/TIME HUD (Orbitron 폰트)
- 우주 배경(별 150개 + 네뷸라)
- 결과 화면에 MAX COMBO / PERFECT / MISS 추가 표시


5. 원본에 적용하는 방법 (지금은 미적용 상태)
--------------------------------------------
[방법 A] 파일을 원본 이름으로 덮어쓰기 — 완전 교체

    cp web/frontend/js/rhythm_game_lab.js  web/frontend/js/rhythm_game.js
    cp web/frontend/rhythm_game_lab.html   web/frontend/rhythm_game.html

  그 다음 rhythm_game.html 안에서 2곳만 수정:
    - <script src="js/rhythm_game_lab.js">  ->  js/rhythm_game.js
    - <title> 을 원래대로 "테스트용 미니게임 - Eye God" 으로
  css/rhythm_game_lab.css 는 파일명 그대로 두고 link 를 유지하면 된다
  (이름이 거슬리면 rhythm_game_theme.css 등으로 rename 후 link 만 고칠 것).
  마무리로 rhythm_game_lab.html / js/rhythm_game_lab.js 삭제.

[방법 B] lab 페이지를 그대로 정식 페이지로 승격 — 가장 안전

  index.html 의 미니게임 링크만 rhythm_game_lab.html 로 바꾼다.
  원본 rhythm_game.html 은 그대로 남아있어서 문제 생기면 링크만 되돌리면 됨.

교체가 쉬운 이유: DOM id(consent-modal, play-screen, pause-modal, result-screen,
display, result-score, consent-confirm/cancel, resume/restart/quit/retry/home-btn)를
원본과 동일하게 맞춰놨고, 소비하는 서버 payload도 동일하기 때문.

선택 사항: 승격 시 데모 모드 코드를 지우고 싶다면 js 파일에서 "DEMO" 로 검색하면
관련 부분(상수 1개 + 분기 4곳 + 데모 드라이버 블록)을 전부 찾을 수 있다.
그냥 둬도 ?demo=1 이 없으면 실행되지 않으므로 무해하다.


6. 데모 모드 (디자인 검토용)
----------------------------
    http://127.0.0.1:8000/rhythm_game_lab.html?demo=1

?demo=1 을 붙이면 로그인·웹캠·캘리브레이션 없이 가짜 노트가 흐르면서 비주얼만
미리 볼 수 있다. 서버에 WebSocket 연결조차 하지 않는다.
데모 드라이버는 서버와 동일한 상수(낙하 3000ms, 스폰 1600~3000ms, 판정 플래시
350ms, 게임 30초)를 써서 실제 게임 템포를 그대로 재현한다.
파라미터 없이 들어가면 원본과 똑같이 로그인·캘리브레이션이 필요한 실제 플레이.


7. 조절 가능한 값 (js/rhythm_game_lab.js 상단 및 각 함수)
---------------------------------------------------------
- FAR_SCALE = 0.26        원근 강도. 낮출수록 소실점이 좁아져 깊이감 증가
- LANE_COLORS             레인별 노트 색 (left=시안 / center=바이올렛 / right=마젠타)
- COLOR_PERFECT, COLOR_MISS  판정 이펙트 색
- layout() 내부           horizonY(0.17), judgeY(0.8), halfNear(폭) 비율
- spawnHitEffect()        파티클 개수(perfect 28 / miss 12), 속도, 수명, 화면 흔들림 세기
- drawHighway()           RUNGS(16) = 흘러오는 그리드 줄 수, 흐르는 속도(now/1500)
- initBackdrop()          별 개수(150), 네뷸라 위치/색/농도

※ NOTE_FALL_DURATION_MS(3000)는 서버 rhythm_game_session.py 의 같은 이름 상수와
  반드시 같아야 한다. 서버 상태(~15fps) 사이를 60fps로 보간할 때만 쓰이며 판정에는
  관여하지 않지만, 값이 어긋나면 노트가 미세하게 튀어 보인다. 서버 값을 바꾸면
  여기도 같이 바꿀 것.


8. 구현하면서 처리한 주의점
---------------------------
- 서버 상태는 ~15fps로 오는데 그대로 그리면 뚝뚝 끊겨 보인다. rAF 60fps 루프를
  따로 돌리고, 프레임 사이에는 경과 시간으로 노트 위치를 보간한다. 판정은 전부
  서버가 하므로 보간은 "보이는 위치"에만 영향을 준다.
- 일시정지 중에는 서버가 직전 last_judgment 값을 매 프레임 계속 재전송한다
  (rhythm_game_session.py 의 process() 가 paused일 때 early return 하면서
  last_judgment 를 비우지 않기 때문). 그대로 두면 정지 중 콤보가 계속 올라가므로
  렌더러에서 state.paused 일 때는 판정 이벤트를 무시하도록 방어했다.
  ※ 백엔드는 건드리지 않았으므로 원본 동작에는 영향 없음.
- 배경(그라디언트 + 네뷸라 3개)은 리사이즈 때 오프스크린 캔버스에 한 번만 그려두고
  매 프레임 blit 한다. 풀스크린 radial gradient 를 매 프레임 3번 칠하면 고해상도
  에서 눈에 띄게 느려진다.
- 파티클은 shadowBlur 대신 미리 만들어둔 글로우 스프라이트를 'lighter' 합성으로
  그린다 (shadowBlur 를 파티클 수백 개에 쓰면 프레임이 떨어짐).


9. 검증한 것 / 검증하지 못한 것
-------------------------------
검증 완료:
- JS 문법 검사 (node --check)
- 원근 수식: 1440x900 기준 소실점 폭 290px → 판정선 폭 1116px(약 3.8배),
  노트 y좌표가 t=0~1.3 구간에서 단조 증가(항상 아래로 낙하)함을 수치로 확인
- 데모 드라이버가 서버와 동일한 스키마/값 범위를 생성하는지
  (필수 키 10개, progress 0~1.3, lane/result 유효값, score = perfect*100 일치)
- 에셋 서빙 200 OK (html/js/css + camera.js/auth.js)
- 로그아웃 상태에서 데모 모드 진입 가능 (/api/auth/me 200)

검증 못 함:
- 실제 캔버스 렌더링 결과. 이 환경에 브라우저 자동화(Playwright)가 없어서
  스크린샷 확인이 불가능했다. 육안 확인은 사용자가 데모 모드로 수행했고
  "디자인 테마 자체는 괜찮다"는 확인을 받은 상태.
- 실제 웹캠 플레이(시선/깜빡임) 상태에서의 렌더링. 렌더러는 서버 payload만
  소비하므로 데모와 동일하게 동작할 것으로 예상되나 실플레이 확인은 아직.
