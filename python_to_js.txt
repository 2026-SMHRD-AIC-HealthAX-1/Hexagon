4. 데이터 흐름 변화
===========================================

지금:
  브라우저 캠 -> JPEG -> WS -> 서버 MediaPipe -> gaze/blink 계산
       -> JSON state -> WS -> 브라우저 렌더

이후:
  브라우저 캠 -> 브라우저 MediaPipe(WASM) -> gaze/blink 계산 -> 브라우저 렌더
       (서버로는 최종 점수만 HTTP POST /api/game-result)

5. 부수적으로 같이 따라오는 구조적 결정들
===========================================

[ ] 캘리브레이션 데이터 저장 위치
    지금은 서버에 data/calibration.json 파일 하나(공용, 원래도
    멀티유저에 안 맞는 구조)로 저장. 브라우저 계산으로 옮기면 이걸
    브라우저 localStorage/IndexedDB에 두거나, 기기 바꿔도 유지되게
    하려면 서버 DB에 사용자별로 저장하도록 스키마를 늘려야 함
    - 이건 선택해야 할 지점.

[ ] 점수 신뢰 모델 변화
    지금은 서버가 게임 로직(리듬게임 노트 판정, 타이밍)을 직접
    계산해서 점수를 만드는 "서버 권위" 구조. 클라이언트로 옮기면
    클라이언트가 계산한 점수를 서버가 그대로 믿고 저장하는 구조가 됨.
    이 프로젝트 성격(개인 건강 기록, 경쟁/랭킹 없음)상 큰 문제는
    아니지만, "신뢰 경계가 서버에서 브라우저로 이동한다"는 구조적
    변화가 생김 - 참고로만 알아둘 부분.

[ ] 브라우저 호환성
    WASM+WebGL 기반이라 구형 브라우저/저사양 기기에서 프레임레이트가
    서버 처리보다 불안정할 수 있음 - 서버 환경은 통제 가능했지만
    이건 사용자 기기마다 편차가 생김.

===========================================
6. 웹 디자인(UI)과의 관계 - 난이도 차이 없음
===========================================

결론: 디자인 작업 난이도는 계산 로직이 파이썬이든 JS든 차이가 없음.

- 일반 페이지(index.html / login.html / hospitals.html / mypage.html /
  analysis.html)는 순수 HTML/CSS(style.css)로 디자인되고, 백엔드는
  Jinja2 같은 템플릿 엔진도 안 써서 애초에 파이썬이 HTML을 렌더링하지
  않음. 이 부분 디자인은 계산 로직이 뭘로 짜여있든 전혀 영향 없음.

- 예외: game.html / rhythm_game.html의 게임 화면은 CSS가 아니라
  canvas에 JS로 직접 그리는 방식(격자 색, 노트 모양, 판정 플래시 색
  등이 game.js / rhythm_game.js의 그리기 코드에 하드코딩)이라, 이
  부분의 시각 디자인은 이미 지금도 "JS 코드"의 영역임. 계산 로직을
  서버 파이썬 -> 브라우저 JS로 옮기더라도, 계산 모듈(gaze.js 등)과
  canvas 그리기 모듈(game.js 등)을 분리된 파일로 유지하면(지금 구조가
  서버-계산/클라이언트-렌더링으로 분리돼 있는 것과 동일한 원칙) 디자인
  난이도에는 변화가 없음.

- 유일한 주의점: 계산과 렌더링이 둘 다 브라우저 JS 안에 있게 되므로
  관리를 소홀히 하면 한 파일에 섞어 넣기 쉬워짐 - 언어 자체의 문제가
  아니라 순전히 구현 습관(파일을 분리해서 관리)의 문제.

===========================================
요약
===========================================

핵심 변화: 계산 로직 파일들의 언어가 파이썬 -> JS로 바뀌고,
WS 스트리밍 프로토콜과 그에 딸린 서버쪽 세션 래퍼들이 통째로 사라짐.

무관하게 남는 것: 인증/DB/외부 API 프록시 계층과 CLI 모드(src/)는
이 변화와 무관하게 그대로 유지됨. 웹 디자인(HTML/CSS) 작업 난이도도
이 변화와 무관 - 게임 화면의 canvas 디자인만 원래도 JS 영역이었음.
