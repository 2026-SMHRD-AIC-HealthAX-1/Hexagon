# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A webcam eye-gaze tracker built on MediaPipe Face Landmarker, grown into a browser-based service called **Eye God** (안구 건조증 기반 백내장 위험 조기 예측 서비스). **Web-only as of 2026-09-15** — a FastAPI web layer in `web/` exposes the eye-gaze minigame, rhythm minigame, calibration menu, and blink monitoring to a browser (using the *browser user's* webcam instead of the server's), a location-based nearby eye-clinic finder that's unrelated to the camera/MediaPipe pipeline, and a login + mypage backed by a real MySQL database and server session cookie — both Google and Kakao login are real OAuth. The core computer-vision logic lives in `src/` — it originally doubled as a standalone desktop CLI app (camera opened locally, UI drawn in OpenCV windows) as well, but that CLI mode has been removed entirely; `src/` is now a plain library of shared CV functions/classes imported only by `web/backend` (both by the still-live server-side backup pages, and historically by the now-deleted CLI). See "Removed: CLI/desktop mode" below for what that removal touched.

This is a git repository (`git status`/`git log` work normally) — pushed to `github.com/StarBlossom99/Eye-God`, with a second `public_ver` remote kept in sync on request.

## Environment setup

- Python 3.12.14 (pinned in `.python-version`).
- The virtualenv is `eye/` — it has all runtime deps installed (mediapipe, opencv, fastapi, uvicorn[standard], httpx, pymysql, torch/ultralytics). Activate it with `source eye/bin/activate`. Note it also carries a lot of packages this app never imports (labelme, PySide6, kaggle, scikit-learn…) from the model-training/labelling work — `requirements.txt` is a curated list of what the web app actually needs, not a `pip freeze` of this venv, so don't regenerate it that way.
- **MySQL**: the web app requires a running MySQL server (any local instance — MySQL Workbench's bundled server, `brew install mysql`, Docker, etc. all work; this project doesn't manage the server itself) plus a database and dedicated user for it (see "Database" below for the exact `CREATE DATABASE`/`CREATE USER` statements).
- `requirements.txt` lists `python-dotenv`, which `web/backend/app.py` needs to load `.env`, `pymysql`, which `web/backend/db.py` needs to talk to MySQL (see "Database" below), and `torch`/`torchvision`/`ultralytics`, which the S-03 photo analysis needs (see "Photo analysis (S-03)" below — torch is a large download, so expect a slow first install). It no longer lists `pyobjc-core`/`pyobjc-framework-Cocoa`/`pyobjc-framework-Quartz`/`screeninfo` — those existed solely for the CLI's OS-specific physical-screen-size lookup (`src/screen.py`), which was deleted along with the rest of CLI mode (see "Removed: CLI/desktop mode" below); the web path has never needed them since it always used the browser's reported viewport size instead.
- **`.env`** (repo root, not committed) holds secrets the web app needs: `NAVER_MAP_CLIENT_ID` (Naver Maps JS SDK, public-ish/domain-restricted identifier), `NAVER_MAP_CLIENT_SECRET` (same NCP Maps application as `NAVER_MAP_CLIENT_ID`, needed only for the server-side Geocoding calls behind the region-search boxes — the JS SDK itself never uses this), `HIRA_API_KEY` (건강보험심사평가원 병원정보 API, a real secret), `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (Google Cloud Console OAuth client, for real Google login — see "Login / My page" below), `KAKAO_CLIENT_ID`/`KAKAO_CLIENT_SECRET` (Kakao Developers REST API key + Client Secret, for real Kakao login — `KAKAO_CLIENT_SECRET` is only required if "클라이언트 시크릿 > 카카오 로그인" is activated in the Kakao console; see "Login / My page" below), `SESSION_SECRET_KEY` (locally-generated random secret that signs the session cookie, unrelated to any external service), and `DB_HOST`/`DB_PORT`/`DB_USER`/`DB_PASSWORD`/`DB_NAME` (MySQL connection — see "Database" below). `web/backend/app.py` auto-loads it via `python-dotenv` and **requires `SESSION_SECRET_KEY` and all five `DB_*` vars to be set** (`os.environ[...]`, no defaults for user/password/name — the app won't start without them, unlike the other keys which degrade gracefully). See `.env.example` for the expected keys — copy it to `.env` and fill in real values. Missing `HIRA_API_KEY` makes the nearby-clinics feature fall back to mock data instead of failing; missing `NAVER_MAP_CLIENT_ID` just skips rendering the map (the clinic list still works); missing `NAVER_MAP_CLIENT_SECRET` makes `/api/place-search` return `503` (search boxes show a "찾을 수 없습니다" message, everything else keeps working); missing `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` or `KAKAO_CLIENT_ID` would break that provider's login buttons/callback (not currently handled gracefully — there's no mock fallback for either anymore).

## Running

All commands run from the repo root (paths like `models/face_landmarker.task` are relative to cwd).

```bash
source eye/bin/activate
uvicorn web.backend.app:app --reload
# open http://localhost:8000 in a browser (not 127.0.0.1 — see "Login / My page" below)
```

Must be run from the repo root — `web/backend/app.py` resolves `models/` relative to cwd. This opens the *browser's* webcam (via `getUserMedia`), not the server machine's camera; works over plain `http://localhost` without HTTPS since localhost is exempt from the secure-context requirement. Requires a running MySQL server reachable with the `DB_*` values in `.env` — see "Database" below.

There is no dedicated test suite/linter/build step for the web app itself, but `tests/{vision,gaze,rhythm}_parity/run.sh` each verify a JS port against its Python original (see "Gaze-tracking minigame"/"Rhythm minigame" below) — worth rerunning after touching any module both sides share.

### Removed: CLI/desktop mode

Through 2026-09-15 this repo also doubled as a standalone desktop CLI tool (`python src/main.py --calibrate`/`python src/main.py`/`python src/main.py --blink`, opening `cv2.VideoCapture(0)` and drawing its own OpenCV windows, storing calibration in a local `data/calibration.json`) alongside the web app — see "What this is" above for why (`src/`'s CV logic started life there before the web layer existed). Once the web app became the only thing anyone actually used, keeping the CLI path alive was pure maintenance weight (a second calibration storage format, a second dependency set, a second thing "Known quirks" had to caveat), so it was removed outright rather than kept as a dead/rollback option:

- **Deleted entirely**: `src/main.py` (all three CLI entry points), `src/screen.py` (OS-specific physical-screen-size lookup, only meaningful for a desktop window), `src/analyze_calibration.py` (matplotlib scatter-plot of `data/calibration.json`), `src/check_json.py` (sample-count printout for the same file), and the `data/calibration.json` file itself (was already gitignored/local-only, so nothing to remove from git history).
- **Trimmed, not deleted** (these modules are still imported by `web/backend` — see below): `src/calibration.py`'s `Calibration.save(path)`/`.exists(path)` (file-based persistence, unused now that calibration lives in MySQL — see "Database"), `src/gaze_game.py`'s `draw(frame)` method + its cv2/numpy imports + its `if __name__ == "__main__"` cv2-window smoke test, and `src/gaze_region_classifier.py`'s `load_calibration_samples(path)` + its `if __name__ == "__main__"` printout (both read the now-gone JSON file). The classes/functions these lived on (`Calibration`, `GazeGame`, `GazeRegionClassifier`, `calculate_region_gaze`, `create_region_points`) are untouched — only their CLI-only extras came out.
- `requirements.txt`: dropped `pyobjc-core`/`pyobjc-framework-Cocoa`/`pyobjc-framework-Quartz`/`screeninfo` (exclusively for `screen.py`, confirmed via `pip show <pkg>`'s `Required-by` in the `eye/` venv before removing — nothing else in the repo depends on them). `matplotlib` and its own transitive deps (`contourpy`/`cycler`/`fonttools`/`kiwisolver`/`pyparsing`/`python-dateutil`/`six`) were **not** removed even though `analyze_calibration.py` was their only direct consumer in this repo — `pip show matplotlib` showed `Required-by: mediapipe` (among others), i.e. `mediapipe` itself depends on `matplotlib`, so pulling it would have broken the actual CV pipeline the web app needs. Always check `Required-by` before dropping a requirements.txt line for "looks unused" reasons; don't assume a package is removable just because no `.py` file in this repo imports it directly.
- **Verified after the cut**: all of `src/{calibration,gaze,gaze_game,gaze_region_classifier,blink_monitor,landmarks}.py` still import cleanly and construct their classes fine; `web/backend/app.py` still imports and boots (`uvicorn` start confirmed serving real traffic); all three parity suites (`tests/vision_parity`, `tests/gaze_parity`, `tests/rhythm_parity`) still pass end-to-end, confirming the trims above didn't touch anything the web path (or its parity tests) actually exercises.
- `README.md`/`WINDOWS_TEST_GUIDE.txt` had their CLI-mode sections removed/rewritten to match (the Windows guide's numbered-step CLI section and several stale calibration-flow references left over from the earlier calibration-menu split were fixed at the same time — see that file directly for current step numbering).

## Architecture — core eye-tracking (`src/`)

A plain library of shared CV functions/classes — no entry point of its own any more (the CLI that used to drive it directly was removed, see "Removed: CLI/desktop mode" above). Everything here is imported by `web/backend` (either `web/backend/sessions/*.py`'s server-side backup-page paths, or historically ported 1:1 into `web/frontend/js/`'s browser-side default paths — see "Gaze-tracking minigame"/"Rhythm minigame" below for which is which).

**Pipeline:** webcam frame -> MediaPipe `FaceLandmarker` (Tasks API, `VIDEO` running mode) -> per-frame face landmarks -> `gaze.compute_gaze()` -> normalized gaze coordinate -> screen mapping -> game logic. `web/backend/landmarker_factory.py` builds the shared `FaceLandmarker`, and `web/backend/sessions/*.py` each drive one WebSocket connection's loop around it (see "Architecture — web service" below).

**Gaze normalization** ([gaze.py](src/gaze.py)): for each eye, `get_eye_bounds` finds the bounding box of the eye landmarks, `get_iris_center` averages the iris landmark positions (using indices from [landmarks.py](src/landmarks.py)), and `normalize_iris_position` expresses the iris center as a 0-1 fraction of the eye's bounding box. `compute_gaze(face_landmarks, smoother)` composes all of this for both eyes, averages left/right, and smooths the result through a `GazeSmoother` (exponential moving average, `alpha=0.2`) passed in by the caller — it's the single entry point the web `sessions/` wrappers use (and `js/vision/gaze.js` is its browser port), so the eye/iris/normalize math itself exists in exactly one place per language.

**Calibration** ([calibration.py](src/calibration.py)): `Calibration` walks a fixed 9-point grid (corners/edges/center of the screen) and holds each point for a few seconds while the caller repeatedly calls `add_sample(gaze_x, gaze_y)`, collecting `{screen: [x,y], gaze: [x,y]}` samples in memory (`self.samples`). Point sequencing/sample windows (`0.3s`–`2.8s` sample window, advance at `3.0s` — shortened from the original `0.5s`/`3.8s`/`4.0s` on 2026-09-17, same 0.3s settle-then-sample-then-settle shape just compressed to a 3s-per-point total instead of 4s) are driven by wall-clock `time.time()`, not frame count or a fixed frame rate — this is why the web version's irregular WebSocket frame arrival doesn't break calibration timing. The class has no file I/O of its own (that was CLI-only and was removed — see "Removed: CLI/desktop mode" above); the caller (`calibration_session.py` on the backend, `js/gaze/calibrationEngine.js` in the browser) is responsible for persisting `self.samples` wherever it needs to go (MySQL via `db.save_calibration()`/`POST /api/calibration` — see "Database" and "Gaze-tracking minigame" below).

**Gaze-to-screen mapping** ([gaze_region_classifier.py](src/gaze_region_classifier.py)): averages gaze samples per calibration point, sorts the 9 points by `(y, x)` to assign region numbers 1–9 topologically, and classifies live gaze by nearest-centroid. Because region numbering is purely topological (based on sort order, not absolute pixel values), the screen size used at game time doesn't need to match the screen size used at calibration time — calibration and game may run at different browser viewport sizes without issue.

**Game** ([gaze_game.py](src/gaze_game.py)): `GazeGame` divides the screen into a 3x3 grid (regions 1-9, matching the classifier's region numbering), picks a random target region different from the last one, and requires the player's classified gaze region to match the target continuously for `required_gaze_time` (0.5s) to score a point and advance. Runs for a fixed `time_limit` (30s). It only tracks `score` — no accuracy or reaction-time metric exists in this class. `get_target_rect()` computes the current target's pixel rectangle from `width`/`height`, called by the web's `GameSession` (sent to the browser as `state["rect"]`) — this class has no rendering of its own (the CLI's cv2-overlay `draw()` method was removed, see above).

**Blink monitoring** ([blink_monitor.py](src/blink_monitor.py)): `BlinkMonitor.update(face_landmarks)` computes eye-aspect-ratio (EAR) per eye from fixed landmark indices, tracks open/closed transitions, and returns `{ear, left_ear, right_ear, is_blinking, blink_count}`. Pure per-frame function, no camera/UI coupling.

### Known quirks in `src/` (don't "fix" without discussion — behavior-preserving is the priority)

- `src/` modules use flat imports (`from calibration import Calibration`, etc.) — there's no package structure. Any code importing from `src/` externally (i.e. `web/backend`, the only remaining consumer) must add `src/` to `sys.path` first.
- Gameplay/calibration/blink parameters (`GazeGame.time_limit=30`, `required_gaze_time=0.5`, `Calibration`'s `0.3s`/`2.8s`/`3.0s` timing window, `BlinkMonitor.threshold=0.20`) are hardcoded defaults, not constructor-exposed settings. Fine as-is for now; only worth revisiting if a settings/difficulty screen is actually planned.

**Data flow**: `Browser (getUserMedia + canvas capture) → WebSocket (binary JPEG frames) → FastAPI → src/ modules via sessions/ → JSON state → WebSocket → Browser (canvas redraw)`. HTTP is used only for serving static files — no HTTP polling anywhere in the real-time paths. **This describes the two backup pages only** (`game_lab.html`, `rhythm_game_lab.html`) as of the client-side conversions below — the default minigame pages and blink monitoring now compute everything in the browser and never stream camera frames anywhere.

**Protocol**: for `/ws/calibration` and `/ws/game`, the client sends one JSON text message first (`{"width": ..., "height": ...}`, the browser's viewport size — the web path has always used this instead of a server-side physical-screen query), then a stream of binary JPEG blobs. `/ws/blink` skips the init message and just streams frames. The server responds to each frame with a JSON state message; `finished: true` (or `type: "error"` for game-without-calibration) signals the client to transition screens and close the socket.

**Per-connection session model**: each WebSocket connection creates its own `FaceLandmarker` instance and its own `frame_timestamp_ms` counter (incremented by 33 per frame received, a fixed-step approximation of VIDEO-mode timestamping) — state lives only in memory for the connection's lifetime, nothing is shared across connections. **Calibration is stored per logged-in user in MySQL**: `calibration_ws.py`/`game_ws.py`/`rhythm_game_ws.py` (all three now backup-only — see "Gaze-tracking minigame" and "Rhythm minigame" below) all read `websocket.session.get("user_id")` right after `accept()` (Starlette's `SessionMiddleware` applies to the websocket ASGI scope exactly like HTTP, so this needs no extra wiring) and close the connection with a `{"type":"error"}` message if it's missing, then pass `user_id` into the session constructor. `CalibrationSession` calls `db.save_calibration(user_id, width, height, samples)` on finish; `GameSession`/`RhythmGameSession` call `db.has_calibration(user_id)` (raising `CalibrationNotFoundError` if missing) and `db.get_calibration_samples(user_id)` — the downstream `calculate_region_gaze()`/`create_region_points()`/`GazeRegionClassifier` in `gaze_region_classifier.py` don't care where the samples list came from, they just consume it in memory. This per-user MySQL storage was a deliberate fix once multiple people (teammates) started testing the web app on a shared server — an earlier single-shared-file design (mirroring what the now-removed CLI used) meant whoever calibrated last would've silently broken everyone else's game session; MySQL sidestepped that from the start of the web app's calibration design, well before the CLI itself was later removed entirely (see "Removed: CLI/desktop mode" above).

**MediaPipe calls run off the shared asyncio event loop, via a dedicated single-thread `ThreadPoolExecutor` per connection** — this was a deliberate fix once team testing raised the concern that one connection's inference would block every other connection's event-loop turn (all three remaining WS routers: `calibration_ws.py`, `game_ws.py`, `rhythm_game_ws.py` — a fourth, `blink_ws.py`, existed here too until it was deleted as dead code on 2026-09-15, see below). Each connection creates its own `ThreadPoolExecutor(max_workers=1)` right alongside its own `FaceLandmarker` (`landmarker = await loop.run_in_executor(executor, create_landmarker)`), then routes every `detect_for_video()` call through that same executor (`await loop.run_in_executor(executor, landmarker.detect_for_video, ...)`), and tears both down together in a `finally` block (`landmarker.close()` via the executor, then `executor.shutdown(wait=False)`). **Why a dedicated single thread instead of the default shared pool** (`run_in_executor(None, ...)`): initial testing produced a false "hang" signal that looked like a GL-context thread-affinity bug — but isolated testing (calling `detect_for_video` directly, bypassing the WS layer entirely) proved calls from a background thread return in ~2ms with no hang at all; the real cause was a flawed test (a face-less synthetic frame), since every router's loop only ever calls `websocket.send_json()` after a face is detected (`if not result.face_landmarks: continue` skips silently otherwise) — a test client sending blank frames will correctly never get a reply, independent of threading. The single-dedicated-thread design was kept anyway (rather than switching to the default shared pool) since it cleanly ties the executor's lifetime to the connection's lifetime with no risk of cross-connection thread contention, and it was the version verified end-to-end (isolated direct-call test, 4 simulated concurrent connections with their own landmarker+thread each, and a real 3-connection concurrent test through the live server) — all before rolling out to routers. Considered as a more complete alternative at the time: moving computation to client-side JS (see `python_to_js.txt`) — that would eliminate this bottleneck even more completely (no shared server resource at all) but was judged too large a structural change for the team-testing phase this fix targeted, so the thread-pool fix shipped instead as the scoped-down version. That alternative has since been done for both minigames (`game.js` and `rhythm_game.js`, the default pages) and for blink monitoring (`home.js`, see "Home page" below) — see "Gaze-tracking minigame" and "Rhythm minigame" below. The three WS routers here still exist and still use this executor pattern, but are reachable only from their respective backup pages (`game_lab.html`, `rhythm_game_lab.html`), not from the default pages.

**All WS routers explicitly check for a disconnect message before looping back to `receive()`**: raw `await websocket.receive()` returns `{"type": "websocket.disconnect"}` without raising on client close, and calling `receive()` again afterward raises `RuntimeError: Cannot call "receive" once a disconnect message has been received.` (not caught by `except WebSocketDisconnect`). Each router's receive loop starts with `if message["type"] == "websocket.disconnect": return` to guard against this — found and fixed in `calibration_ws.py`, `game_ws.py`, and `rhythm_game_ws.py` alike (originally also in the now-deleted `blink_ws.py`); no session class's algorithm logic changed, only the disconnect handling in the loop.

**Blink monitoring is scoped to the home page only** — the WebSocket connection (and thus monitoring) ends when the user navigates away from `index.html`. It's not a persistent background service that survives page navigation; making it one would need some form of state that outlives a single page's WS connection.

**Blink monitoring computes client-side now (converted 2026-09-14, same JS-conversion effort as the two minigames), and its capture loop still runs in a dedicated Worker so it survives the tab being backgrounded**:

- **Capture (worker) vs. inference (main thread) are deliberately split** — this is the one thing that makes blink monitoring's conversion different from the two minigames', and it was discovered through real browser testing, not designed upfront. The first attempt ran `FaceLandmarker` *inside* `blink_capture_worker.js` (a module worker), and it failed for both the GPU and CPU delegate with `Error: ModuleFactory not set.` Root cause (traced into the vendored `vision_bundle.mjs`): MediaPipe's WASM glue loader tries `importScripts()` first and falls back to `document.createElement("script")` — module workers have neither (`importScripts` is a classic-worker-only global; there's no `document` in any worker) — and `vision_bundle.mjs` itself can't be loaded via `importScripts()` either since it's an ES module (`export` statements aren't valid in a classic script). So today's vendored MediaPipe build cannot self-initialize inside a module worker at all, in either delegate mode. The fix: the worker only captures (pulls `VideoFrame`s from the transferred `MediaStreamTrackProcessor` readable stream, throttles to the target fps, converts each to an `ImageBitmap` via `createImageBitmap(frame, {resizeWidth, resizeHeight})`, and transfers the bitmap to the main thread via `postMessage`); `FaceLandmarker`/`BlinkMonitor` run on the main thread (`home.js`), which is the same environment `game.js`/`rhythm_game.js` already use successfully. This still preserves the background-survival goal: worker→main-thread `postMessage` delivery is not timer-based, so it isn't subject to the `setInterval`/`requestAnimationFrame` throttling Chrome applies to hidden tabs — only the *capture* needed to be off-thread, not the inference.
- `camera.js`'s `startWorkerFrameCapture(stream, options, onEvent)` (renamed from `startWorkerFrameSender` — it no longer sends anything over a network) sets up the `MediaStreamTrackProcessor` and worker exactly as before, just without the `wsUrl` it used to hand the worker. `MediaStreamTrackProcessor` is Chromium-only; on unsupported browsers (Firefox/Safari) it returns `null` and `home.js` falls back to a `game.js`-style main-thread `requestAnimationFrame` loop that reads the `<video>` element directly — same inference code path either way (`handleCapturedFrame()` for the worker path, `localVisionLoop()` for the fallback), just a different source of image frames. One easy-to-miss correctness detail inside the worker: every `VideoFrame` pulled from the reader must call `.close()` whether it's kept or throttle-skipped (and every `ImageBitmap` handed to `detectForVideo` must be `.close()`d on the main thread after use), or the browser's cap on outstanding unclosed frames silently stalls the pipeline.
- `landmarker` (the `FaceLandmarker` instance) is cached at module scope in `home.js` and reused across toggle on/off cycles within the same page load (`ensureLandmarker()`, same caching idea as `game.js`'s `prepare()`) — recreating it on every toggle would re-run WASM instantiation each time, adding a multi-second delay to what used to be a near-instant toggle. `BlinkMonitor`/the timestamp source are still recreated fresh each time monitoring starts, so `blink_count` resets to 0 per session like before.
- **`blink_ws.py`/`blink_session.py` (server-side) were deleted on 2026-09-15**: unlike the two minigames, blink monitoring never had a separate backup page, so once client-side computation shipped there was nothing left pointing at `/ws/blink` — a repo-wide review confirmed it and one other candidate (the `*_lab.html` backup pages, intentionally kept — see below; `theme-healthy-lifestyle.css` was the same kind of unreachable code but was later deleted outright, see "Frontend visual design" below) were the only unreachable code, and this was the one safe to remove outright at the time. If server-side blink monitoring is ever needed again, this is the design to restore from git history: a `BlinkMonitor`-wrapping session class + a WS router following the same disconnect-check/`ThreadPoolExecutor` pattern as `calibration_ws.py`.

This was verified end-to-end with a real Playwright + Chromium run (`--use-fake-device-for-media-stream`, not part of the repo — ran from a throwaway scratch directory) against the live dev server: toggling monitoring on reached the "켜짐" status via the worker path (proving `FaceLandmarker` loads successfully on the main thread and the worker successfully delivers frames to it — this is what caught the module-worker bug above, on the *first* run before the capture/inference split existed), the low-blink-rate banner correctly appeared after the 60s window (the fake camera has no real face, so `blink_count` stays 0 the whole time, which is exactly the "too few blinks" condition — confirmed via screenshot), toggling off correctly reset all UI state, and forcing `MediaStreamTrackProcessor` to be absent (`delete window.MediaStreamTrackProcessor`) confirmed the main-thread fallback path also reaches "켜짐"/"꺼짐" correctly. The OS `Notification()` call path was also verified by spying on the constructor with `Notification.permission` forced to `"granted"` (this sandbox's Chrome-for-Testing binary always reports `"denied"` regardless of `context.grantPermissions(["notifications"])`, the same environment limitation noted below) — confirmed it's called with the correct title/body/tag exactly when permission is granted. **What still cannot be verified in this sandbox**: real OS notification popup rendering, and genuine tab-backgrounding throttling behavior (Chrome's internal visibility flag doesn't actually change under this environment's CDP automation, a pre-existing sandbox limitation predating this conversion, not something it introduced) — both need manual confirmation in a real desktop browser: start monitoring, switch to another tab (or minimize) for 20-30s, switch back, and confirm `#blink-count` kept incrementing and/or the alert popup actually appeared.

**Nearby clinics (`clinics.py`/`hospitals.html`/`hospitals.js`) is unrelated to the eye-tracking pipeline** — no MediaPipe, no `src/` code, plain HTTP (not WebSocket) since it's a one-shot lookup, not a continuous stream:

- Flow: `hospitals.html` calls `navigator.geolocation.getCurrentPosition()` on load (the browser's native permission prompt is the "consent" step — no custom modal needed) → `GET /api/clinics?lat=&lng=` → renders the returned list, and separately fetches `GET /api/config` to get `naverMapClientId` and dynamically injects the Naver Maps JS SDK `<script>` tag to render markers.
- `/api/clinics` calls data.go.kr's HIRA "전국 병·의원 찾기" service (`getHsptlMdcncListInfoInqire`, `B552657/HsptlAsembySearchService`), filtered by `QD=D012` (안과's department code in this API — confirmed from the official activation guide, not guessed). That operation's response already includes `wgs84Lat`/`wgs84Lon` per institution, so straight-line distance to the browser's coordinates is computed locally with `haversine_distance_m()` — no separate geocoding or "위치정보 조회" call needed, and no reverse-geocoding step either (an earlier assumption that this API needed 시도/시군구 text turned out to be wrong once the real docs were checked).
- The service is XML-only (`response.text` parsed with stdlib `xml.etree.ElementTree`, not JSON).
- Since department data only refreshes ~daily, all ~4,255 nationwide 안과 entries are fetched once (paginated, `numOfRows=1000`, up to 10 pages) and cached in memory for `CACHE_TTL_SECONDS` (24h) in `clinics.py`'s module-level `_cache` — distance is computed per-request against the cached set, not re-fetched per request.
- If `HIRA_API_KEY` is unset, or the live call raises for any reason, `/api/clinics` silently falls back to `fetch_mock_clinics()` (a handful of synthetic clinics offset from the query point) and reports `"source": "mock"` vs `"source": "hira"` in the response — this is what lets the page work end-to-end before real keys exist.
- Only straight-line distance is shown (e.g. "350m", or "1.23 km" once `distance_m >= 1000` — `formatDistance()` in `js/nearby_clinics.js`, added 2026-09-16) — walking time (the screen design mockup's "도보 5분") was explicitly decided against; not planned.
- **Clinic list items are clickable (added 2026-09-16)**: `createClinicItem()` in `js/nearby_clinics.js` (shared by both the home-page map preview and the full `hospitals.html` list — see below) opens `https://map.naver.com/p/search/{인코딩된 병원명}` in a new tab (`window.open(..., "_blank", "noopener,noreferrer")`) on click, in addition to its existing behavior of re-centering the embedded map on that clinic. Naver's own "길찾기(directions)" deep link (the URL you get from clicking directions on a real Naver Map POI page, shape `/p/directions/-/{encoded},{encoded},이름,id,PLACE_POI/-/transit?...`) uses an internal, undocumented coordinate encoding generated client-side by Naver's own JS at click time — not something this app can reproduce, so a plain name search is the fallback: it opens Naver's search results for the clinic name rather than jumping straight to a directions screen, meaning the user has to click "길찾기" themselves once more from there. `.clinic-item` also gained `cursor: pointer` and a hover state (border/background, matching `.game-item:hover`'s pattern) so it visually reads as clickable, since previously it had a click handler (map re-centering) with no visual affordance at all.
- The "눈 건강 추천 의약품" placeholder section (two static "준비 중" cards) was removed from `hospitals.html` on 2026-09-17 — medication recommendation was decided against as a feature entirely, not just deferred, so its markup (`.medication-grid`/`.medication-card` in `style.css` too) was deleted rather than kept as an empty placeholder.
- **Region-name search** (`GET /api/place-search?query=`, in the same `clinics.py`) lets the user type a region/address instead of relying on geolocation — implemented in three spots sharing the same logic: the home page header search bar, the home page's map-preview search box, and `hospitals.html`'s search box (originally shipped disabled/"준비 중" during the visual migration, activated later since it's the same underlying feature). It proxies to **NCP Maps' Geocoding sub-API** (`https://maps.apigw.ntruss.com/map-geocode/v2/geocode`, headers `x-ncp-apigw-api-key-id`/`x-ncp-apigw-api-key`) — the **same NCP application/account as the Maps JS SDK** (`NAVER_MAP_CLIENT_ID`), just with `NAVER_MAP_CLIENT_SECRET` added and "Geocoding" enabled for that application in the NCP console (unlike the Maps JS SDK, which only needs the Client ID). Response coordinates (`address.y`/`address.x`) are **WGS84 directly** — no coordinate-system conversion needed, unlike Naver's separate "지역 검색"(Local Search) product which was considered and rejected: that one requires a whole separate developers.naver.com/NAVER-API-HUB registration (and Naver has been mid-migration between those two consoles as of 2026, complicating new signups) *and* returns non-WGS84 coordinates. The tradeoff of using Geocoding instead: **it only resolves formal addresses/administrative region names** ("서울특별시 강남구", "강남구") — landmark or station names ("강남역", "서울시청") and business/institution names return no match. This was an explicit, deliberate scope decision (region search only, not business-name search) once the Local Search migration friction became clear. The endpoint's job is narrowly "search text → one coordinate" — everything downstream (fetching nearby clinics, rendering the list/map) reuses the existing `/api/clinics?lat=&lng=` + `js/nearby_clinics.js` code unchanged, via a shared `searchPlace(query)` helper (also in `nearby_clinics.js`) that returns the top result's `{name, address, lat, lng}`. The frontend then calls the same `initHomeMap()`/`init()` functions it already uses for geolocation results — a searched location and a geolocated location are handled identically past that point. If `NAVER_MAP_CLIENT_SECRET` is unset (or Geocoding isn't enabled for the NCP application), `/api/place-search` returns `503` and the search boxes show a "찾을 수 없습니다"-style message rather than crashing (same graceful-degradation spirit as `HIRA_API_KEY`, though there's no mock fallback for search — a missing key just means search doesn't work, not that it returns fake results). Verified working end-to-end with real coordinates (e.g. "서울특별시 강남구" → `37.517305, 127.047502`, matching Gangnam-gu's real location).

  - **Current (v2)**: the `scaleY` transform moved off the content entirely and onto just two things — the `<path class="eye-lens-clip-shape">` living *inside* `<clipPath id="eyeLensClip">`/`#eyeLensClipMypage"` (i.e. the boundary used to clip the sclera/iris/pupil/scan-line group), and the separate `.eye-lens-outline` stroke path drawn on top of it — both share the exact same `d` (`M12,75 C50,28 150,28 188,75 C150,122 50,122 12,75 Z`) so they scale in lockstep and stay visually aligned. There is no longer any `<g class="eye-shape">` wrapper — removed when the transform moved off the content group.
  - **Status source, deliberately simplified from the mockup's plan**: the mockup's own header comment expected a not-yet-decided rule (recent `blink_alerts` frequency was the leading candidate, still undecided) to classify an overall 양호/주의/위험 status. ## Database (`web/backend/db.py`, MySQL)

**Migrated from SQLite to MySQL** (via `PyMySQL`, still deliberately **no ORM/SQLAlchemy** — the query surface is a handful of single-table lookups/inserts, so an ORM would be pure overhead; `db.py` still reads like `clinics.py`/`config.py`, plain functions, no classes). Each helper function opens its own `pymysql.connect()` and closes it before returning — no shared/pooled connection — matching the project's existing "synchronous, local single-user scope" stance (see the MediaPipe note above). Connection config comes from `.env`: `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` — all required, read via `os.environ[...]` (no defaults for user/password/name, so the app won't start without them, same strictness as `SESSION_SECRET_KEY`). `_connect()` uses `pymysql.cursors.DictCursor`, so rows come back as plain dicts already — no more `dict(row)` wrapping needed (SQLite's `sqlite3.Row` required that).

`db.init_db()` runs once at `app.py` import time and creates tables if missing (`CREATE TABLE IF NOT EXISTS`). Since this migration started the MySQL schema fresh (no pre-existing MySQL data to preserve), the old SQLite-era incremental migration functions (`_ensure_game_type_column()`, `_ensure_google_columns()`, `_ensure_kakao_column()`) were dropped entirely — every column (`google_sub`, `kakao_id`, `email`, `game_type`, etc.) is just part of the initial `CREATE TABLE` now, since there's no historical SQLite install to reconcile with. If the schema needs to change again later, a real migration tool (Alembic or hand-written `ALTER TABLE` scripts) would be worth introducing at that point — for now, editing `init_db()`'s `CREATE TABLE` statements is enough since the team can just drop and recreate the local dev database.

**Timestamps are stored as ISO8601 strings in `VARCHAR(64)` columns, not native `DATETIME`/`TIMESTAMP`** — this preserves the exact serialization `_now_iso()` already produced under SQLite (`datetime.now(timezone.utc).isoformat()`), so no date-parsing/timezone-handling code had to change anywhere (session cookies, JSON API responses, `ORDER BY played_at DESC` sorting — ISO8601 strings sort correctly as text). A deliberate choice to keep the DB-engine swap scoped to "same behavior, different storage," not a data-model redesign.

The old `data/eyegod.db` SQLite file is no longer read or written by anything — `db.py` has no notion of it anymore. It's still gitignored but otherwise just an inert leftover file; safe to delete locally.

**Local MySQL setup** (already done for this machine, documented here for reproducing elsewhere): a dedicated `eyegod` database and `eyegod_app` user (not `root`) were created on whatever local MySQL server is already running (this project doesn't install/manage the MySQL server itself — bring your own, e.g. MySQL Workbench's bundled server, `brew install mysql`, Docker, etc.):
```sql
CREATE DATABASE eyegod CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'eyegod_app'@'localhost' IDENTIFIED BY '<password>';
GRANT ALL PRIVILEGES ON eyegod.* TO 'eyegod_app'@'localhost';
```

**Schema**:
- `users(id, provider, created_at, last_login_at, google_sub, email, kakao_id)` — `google_sub`/`email` are nullable (added via `_ensure_google_columns()` migration) and only ever populated for Google logins; `kakao_id` is likewise nullable (added via `_ensure_kakao_column()` migration) and only ever populated for Kakao logins. `google_sub`/`kakao_id` are how the backend recognizes a returning user for each provider — looked up via `db.get_user_by_google_sub()` / `db.get_user_by_kakao_id()` on every callback. `email` is populated by whichever provider the user logged in with last (nullable — Kakao users typically won't have one, see "Login / My page" above).
- `game_records(game_record_id, user_id, game_type, score, played_at)` — one row per finished minigame, `game_type` is `'gaze'` (S-05) or `'rhythm'` (test rhythm game, see "Rhythm minigame" below).
- `analysis_results(analysis_id, user_id, cataract_prob, redness_ratio, analyzed_at)` — one row per finished S-03 photo analysis, written by `routers/analysis.py`. **The analyzed photo itself is never stored** (see "Photo analysis (S-03)" below) — only these numbers survive the request. Both are `FLOAT` 0–1 ratios, not display strings: the 정상/주의 필요/위험 grade is a *derived* value (`classify_risk()` applied to `cataract_prob`), so storing the grade would silently disagree with the thresholds if those ever move — `GET /api/mypage` recomputes it on read instead. The columns were originally `cataract_risk`/`redness` `VARCHAR(20)` back when nothing wrote to the table; they were changed to numeric when S-03 became real. If a teammate's local DB still has the old empty table, `DROP TABLE analysis_results;` and let `init_db()` recreate it (it was always empty — nothing ever wrote to it).
- `calibration_data(user_id PRIMARY KEY, data, updated_at)` — per-user calibration storage for the web path (see "Per-connection session model" above for the multi-user motivation). `data` is `{version, screen:{width,height}, samples}` (the same shape `src/calibration.py`'s now-removed file-save method used to write, back when that existed — see "Removed: CLI/desktop mode" above), stored as a TEXT blob rather than normalized into rows, since nothing queries into individual samples via SQL and the downstream `gaze_region_classifier.py` functions just want that list back as-is. `db.save_calibration()`/`has_calibration()`/`get_calibration_samples()` are the three functions (`save_calibration` upserts via the same UPDATE-then-INSERT-if-`rowcount==0` idiom as `touch_user_login()`).
- `blink_alerts(blink_record_id, user_id, triggered_at)` — one row per time the home page's low-blink-rate alert fires (see "Low-blink-rate alert" above), **not** a log of raw per-frame blink data. `db.log_blink_alert(user_id)` inserts a row; `home.js`'s `showBlinkAlert()` calls `POST /api/blink-alert` every time it triggers, fire-and-forget (`fetch(...).catch(() => {})`, no awaiting/error surfaced to the user) since blink monitoring works without login (`index.html` doesn't require it) and an unauthenticated call correctly 401s and is silently dropped. The intent (per explicit user request) is letting the user later judge whether they have a risky blinking habit from how often the alert fired — not building a full blink-rate time series. **Nothing reads this table back yet** — the mypage trend graph shipped 2026-09-16 (see "Mypage history tabs" above) only covers the same 4 categories as the 누적 기록 tab (cataract/redness/gaze/rhythm); display of blink-alert frequency (e.g. "이번 주 경고 N회") is still undecided/unimplemented.

**Session cookie (`SessionMiddleware`, added in `app.py`)**: signed via `itsdangerous` (new dependency — Starlette's `SessionMiddleware` requires it), `secret_key` from `.env`'s `SESSION_SECRET_KEY` (a locally-generated random value, unrelated to either provider's credentials), `max_age` 30 days, `same_site="lax"`. **`https_only=False`** — correct only because this runs on `http://localhost` today; **this must become `True` before any real-domain deployment**, or the session cookie would be sent over plain HTTP. `request.session["user_id"]` is the one thing every protected endpoint trusts; nothing else is.

Both OAuth callbacks (`GET /api/auth/google/callback`, `GET /api/auth/kakao/callback`) set `request.session["user_id"]` the same way, so downstream endpoints don't need to know or care which provider was used — the signed session cookie is the only trust boundary for every subsequent request.

**Endpoints** (`routers/auth.py` unless noted):
- `GET /api/auth/google/login?next=` — starts the real OAuth flow: generates a CSRF `state`, stashes it (and `next`) in the session, redirects to Google's consent screen. Redirect URI is derived via `request.url_for("google_callback")`, so the app must be accessed as `http://localhost:8000` (matching what's registered in Google Cloud Console), not `127.0.0.1`.
- `GET /api/auth/google/callback` — verifies `state`, exchanges `code` for a token (`https://oauth2.googleapis.com/token`), fetches `{sub, email}` (`https://openidconnect.googleapis.com/v1/userinfo`) via `httpx.AsyncClient` (same async-client pattern as `clinics.py`), looks up/creates the user by `google_sub`, sets the session cookie, redirects to `next`.
- `GET /api/auth/kakao/login?next=` — same CSRF `state` pattern as Google, redirects to Kakao's consent screen (`https://kauth.kakao.com/oauth/authorize`). Redirect URI is derived via `request.url_for("kakao_callback")`, so the app must be accessed as `http://localhost:8000` (matching what's registered as the "카카오 로그인 리다이렉트 URI" under Kakao Developers → 내 애플리케이션 → [앱] → [플랫폼 키] → REST API 키), not `127.0.0.1`.
- `GET /api/auth/kakao/callback` — verifies `state`, exchanges `code` for a token (`https://kauth.kakao.com/oauth/token`, including `client_secret` only if `KAKAO_CLIENT_SECRET` is set), fetches `{id, kakao_account.email}` (`https://kapi.kakao.com/v2/user/me`) via `httpx.AsyncClient`, looks up/creates the user by `kakao_id`, sets the session cookie, redirects to `next`.
- `GET /api/auth/me` — `{logged_in: false}` or `{logged_in: true, user_id, provider, logged_in_at}` from the current session; this is what `js/auth.js`'s `syncAuthWithServer()` polls on every gated page load.
- `POST /api/auth/logout` — clears the session.
- `POST /api/game-result` (`routers/mypage.py`) — body is now just `{score, game_type}` (`game_type` defaults to `"gaze"`); the user comes from `Depends(get_current_user_id)` (in `auth.py`), which 401s if there's no session. Called by `showResult()` in all four minigame entry points (`game.js`, `game_lab.js`, `rhythm_game.js`, `rhythm_game_lab.js`) — same endpoint/payload regardless of which computation path produced the score.
- `GET /api/mypage` (`routers/mypage.py`) — same session dependency, no query params anymore; returns `{logged_in_at, last_game_gaze, last_game_rhythm, cataract_risk, redness, eye_status_risk}`. `cataract_risk`/`redness` come from the most recent `analysis_results` row (`{prob, label, analyzed_at}` / `{ratio, analyzed_at}`, or `null` if S-03 has never been run) — `label` is computed on read via `classify_risk()`, not stored. `eye_status_risk` (added 2026-09-16) is a separate recency-weighted value over the most recent 3 rows, `{prob, label, sample_count}` or `null` — see "Home page" above (→ "Status source") for why it's distinct from `cataract_risk` and how the weighting works. Read by `mypage.js` and the home page's health-summary card (`home.js`); `eye_status_risk` specifically feeds the eye-icon banner (`js/eyeStatus.js`), while `cataract_risk` still feeds the plain stat-grid cell on both pages.
- `GET /api/mypage/history?category=` (`routers/mypage.py`, added 2026-09-16) — same session dependency; `category` is one of `cataract`/`redness`/`gaze`/`rhythm` (`400` otherwise), returns `{records: [...]}` with every one of that user's rows for the category, newest first, in the same per-record shape `GET /api/mypage` already uses. Returns `{ok: true, cataract_prob, cataract_label, redness_ratio}` and writes one `analysis_results` row, or `{ok: false, missing, message}` (HTTP 200) when the eye regions weren't found, in which case nothing is saved and the user is asked to retake. `400` for an empty/undecodable body, `413` over 15MB.
- `POST /api/blink-alert` (`routers/mypage.py`) — same session dependency (401 if not logged in); no body, just records "now" for the current user into `blink_alerts`. See the `blink_alerts` schema entry above.

- `GET /api/calibration` / `POST /api/calibration` (`routers/calibration_api.py`) — both use the same session dependency. GET returns `{has_calibration, samples}` for the current user, `samples` being the same `[{"screen":[x,y],"gaze":[gx,gy]}, ...]` shape `db.get_calibration_samples()` already returned server-side; used by both `game.js` and `rhythm_game.js` on game entry to decide whether to run an inline calibration first (see "Gaze-tracking minigame" below), and by the rhythm minigame's `js/rhythm/calibration.js` to convert existing samples into laneX. POST takes `{width, height, samples}` and calls `db.save_calibration()` directly — called by both `game.js` and `rhythm_game.js` whenever their inline calibration flow finishes; this is the only way a browser-computed calibration gets persisted, since `calibration_ws.py`/`calibration_session.py` (the old write path) only run for the backup page.

## Inline calibration (both minigames' default pages)

Both `game.js` and `rhythm_game.js` run their own 9-point calibration inline, immediately before their own game, rather than through any separate page. Calibration's entry point has moved twice: it originally lived inline in `game.html` only (forcing a fresh calibration on every play), was split out into a standalone `calibration.html` menu on 2026-09-15 (reachable from the home page's mini-game panel), and was folded back into each game's own entry flow on 2026-09-16 — a separate menu card turned out to be an unnecessary extra click when each game could just ask before starting. `calibration.html`/`js/calibration.js` no longer exist; both entry points below duplicate the same small pattern instead of sharing a page.

**The flow, identical in both `game.js` and `rhythm_game.js`**, runs after the webcam consent modal is accepted and the MediaPipe model has loaded (calibration needs the same camera/model the game itself needs, so one consent step covers both):
1. `GET /api/calibration` (via `game.js`'s `checkCalibration()`, or `rhythm_game.js`'s `js/rhythm/calibration.js#fetchLaneX()`) checks for existing samples.
2. **No calibration on file**: `showGuide()` (`js/guide.js`) shows a single-button notice — "캘리브레이션 데이터가 없습니다 / 캘리브레이션을 진행해주세요" — then runs the calibration flow directly.
3. **Calibration on file**: `showChoice()` (`js/guide.js`, added alongside `showGuide()` for this) shows "기존 캘리브레이션 데이터를 기반으로 게임을 진행할까요?" with two buttons — "게임 진행" (skip straight to the game guide, reusing the existing samples) or "새로 캘리브레이션 진행" (run the calibration flow, same as step 2).
4. **The calibration flow itself** (when run): a calibration-specific guide modal ("지금부터 화면에 나타나는 9개의 점을...") → the play-screen canvas is unhidden and a `CalibrationEngine` (`js/gaze/calibrationEngine.js`, unchanged since before the split — same 9-point grid/timing port) drives the same `visionLoop` the game itself uses, branched by a `calibrationEngine` vs. `gameEngine` variable rather than two separate loops. On finish, `saveCalibration()` (`js/gaze/calibrationApi.js`) POSTs the samples, and each caller derives what it needs straight from the just-finished `calibration.samples` in memory (`regionPoints` via `calculateRegionGaze`/`createRegionPoints` in `game.js`; `laneX` via `js/rhythm/calibration.js`'s `computeLaneX(samples)` in `rhythm_game.js`) — no re-fetch of what was just saved. A save failure alerts and restarts the calibration engine directly (not the whole flow, so the guide modal doesn't reappear).
5. Either path ends the same way: the game's own guide modal, then the game itself.

Retrying after a result ("다시하기") never re-checks calibration — it reuses whatever `regionPoints`/`laneX` are already held in memory for that page load.

## Rhythm minigame (`rhythm_game.html`, "시선 추적 리듬게임")

A second minigame alongside the S-05 gaze game, linked from the home page's mini-game panel (`.game-list`, see "Home page" above); gated by `requireLogin()` like every other service screen. A correctly-timed catch scores points and shows "Perfect"; a mistimed or missed catch shows "Miss". ESC pauses the game with a resume/restart/quit menu.

**Two computation paths exist side by side** — this was the first (and so far only) feature converted per the plan in `python_to_js.txt`:

## Shell game prototype (야바위, `shell_game_test.html`)

Added 2026-09-17 as a quick prototype, explicitly **not** planned for the real service yet — not linked from `index.html`'s mini-game panel or anywhere else, not gated by `requireLogin()`, no camera/MediaPipe/WebSocket, and no DB write at all (score is shown on-screen only, per explicit instruction — `POST /api/game-result` is never called). Reachable only by typing the URL directly. Implementation itself was confirmed working end-to-end (see the QA bullet below) and sized/tuned per feedback the same day — it's considered feature-complete as a prototype and deliberately left unpromoted pending a decision to ship it. See "Promoting to a real feature" below for exactly what that would take.

- **Gameplay**: 3 cups, one hidden ball. Each round: briefly show which cup the ball goes under (`reveal` phase, cup lifts to expose the ball then lowers), shuffle continuously for a fixed 15s (`shuffle` phase — see below for how "continuous" is enforced), then wait for a mouse click on a cup (`choose` phase, camera-free — this is the one minigame-shaped thing in the repo with zero gaze/blink involvement). A correct click scores points and starts the next round (skipping straight to `reveal`, no repeat of the cup-entrance animation — see `startRound(isFirstRound)` in `js/shell_game.js`); a wrong click ends the game and shows a result screen. Each level shuffles faster and is worth more points than the last (`swapDurationForLevel()`/`scoreForLevel()` in `js/shell_game.js` — duration steps down from 650ms toward a 220ms floor, `SWAP_DURATION_STEP_MS=80` per level (doubled from an initial 40 same-day, per feedback that the ramp-up felt too gradual — now hits the floor around level 7 instead of level 11), score steps up from 100 by 50 per level).
- **Sizing (2026-09-17, same-day follow-up)**: cups/ball felt too small against the canvas on first pass, so both the props and the canvas grew together — `CUP_WIDTH`/`CUP_HEIGHT`/`BALL_RADIUS`/`LIFT_HEIGHT` all scaled up (120→160 / 110→145 / 16→22 / 120→140), and `CANVAS_W`/`CANVAS_H` went from 640×380 to 700×440 specifically because bigger cups need more headroom above the table line so a fully-lifted cup (`LIFT_HEIGHT + CUP_HEIGHT`) doesn't clip the canvas's top edge during `reveal`/`result` — enlarging the props without also growing the canvas would have cut the cup off mid-animation. `SLOT_X` fractions moved from `[0.2, 0.5, 0.8]` to `[0.16, 0.5, 0.84]` to keep a comfortable gap between the now-wider rest-position cups. `css/shell_game_theme.css`'s `#game-canvas` `max-width`/`aspect-ratio` and `.screen`'s `max-width` (680px→740px) were updated to match.
- **Continuous shuffle, no gaps**: the explicit requirement was that cup movement never visibly pauses during the 15s shuffle. Implemented as a swap-chaining scheduler in `updateShuffle()` — two of the three cups (randomly chosen each time) swap slots via an eased arc motion (one arcs higher/"over", the other lower/"under", chosen randomly per swap for visual variety), and the moment one swap's animation reaches `t>=1` the next swap starts immediately within the same `requestAnimationFrame` callback chain (no `setTimeout` gap between them). The 15s window is only checked for expiry *between* swaps (right when one finishes) rather than by hard-stopping mid-motion, so cups always land exactly on a rest slot position before `choose` begins (this also matters for click hit-testing, which assumes cups are at rest).
- **A real bug caught during manual QA (fixed same day)**: `update()`'s `shuffle` case called `updateShuffle(now)` (which can transition the phase to `choose` mid-call) and then unconditionally overwrote `#phase-message` with the shuffle countdown text — so the moment shuffle ended, the correct "클릭하세요" prompt got immediately stomped by a stale "남은 시간 0초" that then never changed again, even though the game was already accepting clicks underneath. Caught via a Playwright-driven run (headless Chromium, already available locally via `npx playwright`) that clicked the canvas despite the stuck-looking text and confirmed the click *was* processed — proving it was a display-only bug, not a state bug. Fixed by guarding the countdown-text write with `if (state.phase === "shuffle")` after the `updateShuffle()` call. Worth remembering if this file's phase-transition-inside-an-update-branch pattern gets copied elsewhere.
- **No parity test** (unlike the gaze/rhythm minigames) — there's no Python original to port from and no server-side counterpart at all, so `tests/` has nothing for this page.
- `css/shell_game_theme.css` is a fixed casino-felt (dark green/gold) theme independent of the site's dark-mode toggle, same rationale as `rhythm_game_theme.css` — the page doesn't link `style.css` at all since it has no shared header/nav to stay visually consistent with.

## Photo analysis (S-03) — `analysis.html` + `POST /api/analysis` + `models/`

Upload an eye photo → server returns 백내장 의심 확률 + 등급 and 충혈도 → shown on the page and saved to `analysis_results`. This is the one feature that runs **real trained models server-side** (everything else CV-related is either MediaPipe in the browser or MediaPipe on a WS connection).

**The models and the pipeline live outside `web/`**, in `models/` and `AI/`, and predate the web wiring:

```
models/
├── eye_analysis.py       # the end-to-end pipeline the web layer calls
├── eye_seg/              # yolo26n-seg: sclera + iris_pupil segmentation
│   ├── eye_seg.pt          6.3MB, committed — clone and run, no separate download
│   ├── inference.py        standalone single-photo test
│   ├── batch_inference.py  standalone folder test
│   └── redness_ratio.py    sclera mask -> red-pixel ratio (충혈도)
└── cataract_cls/         # yolo11n-cls: cataract vs normal, trained on CROPPED iris_pupil images
    ├── best.pt             3.1MB, committed — same as above
    ├── infer.py            standalone classification + the 정상/주의 필요/위험 thresholds
    └── 백내장 학습.ipynb    the Colab training notebook
```

`AI/AI_Flow.txt` is the authoritative design doc for all of this (how the two models split the work, what's tuned vs. still guesswork, what's deliberately deferred). **Read it before touching anything under `models/` or `AI/`** — several of its decisions look like oversights otherwise.

Both `.pt` weights are committed (~9.4MB total) so a clone can run S-03 without a separate download — unlike `web/frontend/vendor/mediapipe/`, which is fetched by a script. What stays gitignored in those folders is the *training data* and test/result images (`models/eye_seg/dataset/`, `test_image.jpg`, …): those are large and, more importantly, may include third-party images whose licensing was never established (some carry stock-photo watermarks) — the same reason `AI/cataract/`, `AI/redness/` and `reference_img/` are excluded. Keep that split if you add files here. Note git keeps every version of a binary forever, so re-committing retrained weights repeatedly will grow the repo permanently.

- **Pipeline** (`models/eye_analysis.py`): run `eye_seg` **once** per photo, then split its two masks — `iris_pupil` gets cropped and classified by `best.pt` (백내장 확률), `sclera` gets the red-pixel ratio (충혈도). If either region is missing, it returns `{"ok": False, "missing": [...]}` and the user is asked to retake rather than getting a half-result.
- **The crop is load-bearing, not cosmetic**: `cataract_cls` was trained on cropped `iris_pupil` images, so feeding it a full uncropped photo silently loses accuracy (no error, just worse numbers). `eye_analysis.py` therefore imports the crop helpers (`find_best_iris_pupil_box`, `pad_and_clip_box`, `PADDING_RATIO`) straight from `AI/scripts/crop_iris_pupil.py` — the same code that built the training set — rather than copying the constants. Don't "clean that up" into a local copy; a drifted `PADDING_RATIO` is exactly the failure this avoids.
- **Thresholds**: `< 30%` 정상, `30–70%` 주의 필요, `≥ 70%` 위험 (`models/cataract_cls/infer.py`'s `LOW_THRESHOLD`/`HIGH_THRESHOLD`, deliberately conservative — see `AI_Flow.txt` section 3 for why a single 0.5 cut was rejected). The probability is always shown *alongside* the grade. This is the single source of truth: `routers/mypage.py` imports `classify_risk` rather than reimplementing the bands.
- **주의 필요/위험 grades trigger a nearby-clinic nudge** (added 2026-09-16): `analysis.js` checks the label string the backend returned (`data.cataract_label`, matched against exactly `"주의 필요"`/`"위험"` — the same two non-정상 strings `classify_risk()` can return) and shows `#clinic-recommend` (a `.status-banner.error`-styled box) with a fixed message plus a button to `hospitals.html`. Purely client-side string matching, not a separate API call — if `classify_risk()`'s return strings ever change, this comparison has to change with it. Hidden again on 다시 분석하기 along with the rest of the result.
- **충혈도 is a raw number with no grade attached, on purpose.** Its HSV thresholds are known to over-report (`AI_Flow.txt` section 2's 2026-09-11 measurements: nearly every clinical close-up lands at 50–90% because of lighting/white balance), so `redness_ratio.py`'s `classify_redness()`/`CAUTION_RATIO`/`SEVERE_RATIO` exist but are **not called** by the pipeline, and `analysis.html` labels the number as 참고용. Tuning them is still an open task. Don't wire that grade in until the reference photos exist.
- **Probability calibration is deferred**: the percentages are raw softmax confidence, which tends to be overconfident. `AI/classification_prob.txt` has the temperature-scaling procedure to apply when someone picks it up (`AI_Flow.txt` section 5).

**Privacy design — the uploaded photo is never written to disk.** This was an explicit requirement, and it's why two things are shaped unusually:

1. **`POST /api/analysis` takes the raw request body, not a multipart form.** Starlette's `UploadFile` spools to a temp file on disk once the upload exceeds ~1MB, which phone photos routinely do — the file gets cleaned up, but the original still hits the disk on the way through. Reading `await request.body()` keeps it in memory for its whole life. Side benefit: no `python-multipart` dependency. The frontend correspondingly does `fetch("/api/analysis", {method: "POST", body: file})` with the file as the body. A 15MB cap (`MAX_UPLOAD_BYTES` → 413) exists because the body is buffered in memory.
2. **The pipeline takes a decoded array, not a path.** `analyze_image(img_bgr)` is the entry point the router uses (`cv2.imdecode` on the body bytes); `analyze(path)` is a thin wrapper kept for the CLI. Verified that YOLO's path input and array input produce byte-identical boxes/confidences/masks, so this costs nothing in accuracy. Also confirmed inference writes nothing itself (no `runs/` dir), and that a >1MB upload leaves the temp dir file count unchanged.

Only the resulting numbers are persisted (`analysis_results`, see "Database" above). If you add anything to this path, keep the photo out of the filesystem and out of logs.

**Other operational notes**:
- The two YOLO models are loaded once and cached at module scope in `eye_analysis.py` (`_load_model()`) — without it every request re-reads the weights.
- Inference runs via `run_in_executor` for the same reason the WS routers use a thread pool: a YOLO forward pass holds the CPU for a few hundred ms and would otherwise stall every other request on the event loop.
- `web/backend/app.py` adds `models/` to `sys.path` (alongside `src/`/`scripts/`) so `import eye_analysis` works under the repo's flat-import convention. `eye_analysis.py` in turn adds `models/eye_seg`, `models/cataract_cls`, and `AI/scripts` itself.
- **Requires `torch`/`torchvision`/`ultralytics`** (now in `requirements.txt`; they were installed locally but unlisted before S-03 went live, so a fresh clone would have been missing them). torch is a large download.
- `models/eye_analysis.py` still works standalone: `python models/eye_analysis.py --image 눈사진.jpg`.

## Frontend visual design (migrated from `Eye_God_New_HTML/`)

The user supplied a separate `Eye_God_New_HTML/` folder — a designer-provided visual prototype for all 6 screens (index/login/analysis/game/hospitals/mypage). `clinics.html`/`clinics.js` were renamed to `hospitals.html`/`hospitals.js` to match the mockup's naming; the backend's `clinics.py` module and `/api/clinics` route were deliberately left unrenamed since renaming them would have been a pointless backend touch for a frontend-only migration.

All 7 pages were missing `<meta name="viewport" content="width=device-width, initial-scale=1">` until this was found and fixed — without it, mobile browsers render at a virtual desktop-width viewport (~980px) and zoom out to fit, so `style.css`'s `@media (max-width: 850px)`/`(max-width: 500px)` rules never actually trigger on a real phone even though they work correctly when narrowing a desktop browser window. At `max-width: 500px`, `header.top-bar`'s three children (`.logo`, `.header-search`, `#auth-area`) also get an explicit `order` (1/3/2) plus `.header-search { flex: 1 1 100%; }` — without this, plain `flex-wrap` breaks lines purely by available width, so exactly where the header wrapped (and thus whether the search bar ended up next to the logo, next to the login button, or alone) varied by device width instead of being consistent. Now mobile always gets logo+login on one row and the region-search bar filling its own row below, regardless of exact screen width.

## Data/model files

- `models/face_landmarker.task` — MediaPipe Face Landmarker model, loaded via [web/backend/landmarker_factory.py](web/backend/landmarker_factory.py). Required for anything to run.
- `web/frontend/vendor/mediapipe/` — **gitignored, browser-side counterpart to the file above.** Populated by `python scripts/setup_mediapipe.py` (repo root, stdlib only): MediaPipe's browser WASM engine (`@mediapipe/tasks-vision`, ~11MB) plus a copy of `face_landmarker.task` (3.6MB), served by the existing `StaticFiles` mount so the browser can fetch them at `/vendor/mediapipe/...`. Needed for both default (client-side computation) minigame pages — `game.html` (S-05, see "Gaze-tracking minigame" above) and `rhythm_game.html` (see "Rhythm minigame" above), each of which also runs its inline calibration step (see "Inline calibration" above) off these same assets; not needed by either backup page or anything else in the app. Re-run with `--force` to refresh after bumping `PACKAGE_VERSION` in the script.
  - **Auto-installed at server startup since 2026-09-15**: before this, a fresh clone's first `uvicorn web.backend.app:app --reload` would start fine, but the *first* visit to any client-side minigame/calibration page would fail with a "얼굴 인식 모델을 불러오지 못했습니다" alert until someone manually ran the script — easy to miss since `README.md`'s web-mode instructions never mentioned this step (only `WINDOWS_TEST_GUIDE.txt` did). `web/backend/app.py` now adds `SCRIPTS_DIR` (`scripts/`) to `sys.path` alongside `SRC_DIR`/`BACKEND_DIR` at the top (same flat-import convention as `src/`) and, right after `db.init_db()`, imports `setup_mediapipe` and calls `setup_mediapipe.already_installed()` — if that's `False`, it runs `download_and_extract()` + `copy_model()` synchronously before the app finishes constructing. This means the *first* `uvicorn --reload` after a clean clone blocks for a few seconds while it downloads (~10MB), printing the same `[1/3]`/`[2/3]`/`[3/3]` progress lines `setup_mediapipe.py`'s own `main()` prints; every subsequent start (including every `--reload` restart) is a no-op since `already_installed()` short-circuits. A download failure (no network, registry unreachable, etc.) is caught and logged rather than crashing the server — the rest of the app (login, hospitals, blink monitoring, etc.) needs none of this, so it still boots fine, and the pre-existing per-page alert remains as the fallback signal telling whoever's running the server to run `python scripts/setup_mediapipe.py` manually. Verified by renaming `vendor/mediapipe/` away, importing `web.backend.app` directly (download ran, files reappeared, ~10.2MB), reimporting (silently skipped, no re-download), and a real `uvicorn` boot confirming `/vendor/mediapipe/vision_bundle.mjs` serves `200`.
- `data/calibration.json` — **removed 2026-09-15 along with the rest of CLI mode** (see "Removed: CLI/desktop mode" above) — it was already gitignored/local-only and had been unused by the web path since calibration moved into the `calibration_data` MySQL table (keyed by the logged-in user's id); nothing reads or writes it any more, and the `data/` directory now holds no application files at all.
- `data/eyegod.db` — **dead file, no longer used.** Left over from before the MySQL migration (unrelated to the CLI removal above); nothing in the app reads or writes it anymore. Safe to delete.
