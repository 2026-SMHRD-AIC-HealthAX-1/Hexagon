# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A webcam eye-gaze tracker built on MediaPipe Face Landmarker, being grown into a browser-based service called **Eye God** (안구 건조증 기반 백내장 위험 조기 예측 서비스). The core computer-vision logic lives in `src/` and was originally a desktop CLI app (camera opened locally, UI drawn in OpenCV windows). A FastAPI web layer in `web/` now exposes the eye-gaze minigame and blink monitoring to a browser (using the *browser user's* webcam instead of the server's), a location-based nearby eye-clinic finder that's unrelated to the camera/MediaPipe pipeline, and a login + mypage backed by a real SQLite database and server session cookie — both Google and Kakao login are real OAuth.

Not a git repository — there is no `.git` here, so there's no commit/branch history to consult.

## Environment setup

- Python 3.12.14 (pinned in `.python-version`).
- The virtualenv is `eye/` — it has all runtime deps installed (mediapipe, opencv, pyobjc for macOS screen APIs, screeninfo for Windows, fastapi, uvicorn[standard], httpx). Activate it with `source eye/bin/activate`.
- `requirements.txt` lists `pyobjc-core`/`pyobjc-framework-Cocoa`/`pyobjc-framework-Quartz` (macOS screen size in [screen.py](src/screen.py)) and `screeninfo` (Windows screen size) with `sys_platform` environment markers, so `pip install -r requirements.txt` only pulls the OS-appropriate one on each platform — both used to be missing entirely (silently relying on `eye/`'s already-installed set) until this was fixed for cross-platform testing. It also lists `python-dotenv`, which `web/backend/app.py` needs to load `.env`.
- **`.env`** (repo root, not committed) holds secrets the web app needs: `NAVER_MAP_CLIENT_ID` (Naver Maps JS SDK, public-ish/domain-restricted identifier), `NAVER_MAP_CLIENT_SECRET` (same NCP Maps application as `NAVER_MAP_CLIENT_ID`, needed only for the server-side Geocoding calls behind the region-search boxes — the JS SDK itself never uses this), `HIRA_API_KEY` (건강보험심사평가원 병원정보 API, a real secret), `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (Google Cloud Console OAuth client, for real Google login — see "Login / My page" below), `KAKAO_CLIENT_ID`/`KAKAO_CLIENT_SECRET` (Kakao Developers REST API key + Client Secret, for real Kakao login — `KAKAO_CLIENT_SECRET` is only required if "클라이언트 시크릿 > 카카오 로그인" is activated in the Kakao console; see "Login / My page" below), and `SESSION_SECRET_KEY` (locally-generated random secret that signs the session cookie, unrelated to any external service). `web/backend/app.py` auto-loads it via `python-dotenv` and **requires `SESSION_SECRET_KEY` to be set** (`os.environ["SESSION_SECRET_KEY"]`, no default — the app won't start without it, unlike the other keys which degrade gracefully). See `.env.example` for the expected keys — copy it to `.env` and fill in real values. Missing `HIRA_API_KEY` makes the nearby-clinics feature fall back to mock data instead of failing; missing `NAVER_MAP_CLIENT_ID` just skips rendering the map (the clinic list still works); missing `NAVER_MAP_CLIENT_SECRET` makes `/api/place-search` return `503` (search boxes show a "찾을 수 없습니다" message, everything else keeps working); missing `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` or `KAKAO_CLIENT_ID` would break that provider's login buttons/callback (not currently handled gracefully — there's no mock fallback for either anymore).

## Running

All commands run from the repo root (paths like `models/face_landmarker.task` and `data/calibration.json` are relative to cwd).

### CLI / desktop mode (original, unchanged)

```bash
source eye/bin/activate

# Step 1: calibrate — shows a 3x3 grid of points on screen, one at a time,
# and records normalized iris position while you look at each. Press q to abort.
python src/main.py --calibrate

# Step 2: run the gaze-tracking game using data/calibration.json from step 1
python src/main.py

# Blink monitoring (prints to console)
python src/main.py --blink
```

Other standalone scripts (run after calibration data exists):

```bash
python src/gaze_region_classifier.py   # print the 9 calibrated region gaze-centroids
python src/analyze_calibration.py      # scatter-plot calibration samples per screen point (matplotlib)
python src/check_json.py               # print sample counts per calibration screen point
```

### Web mode (browser-based)

```bash
source eye/bin/activate
uvicorn web.backend.app:app --reload
# open http://127.0.0.1:8000 in a browser
```

Must be run from the repo root — `web/backend/app.py` resolves `models/` and `data/` relative to cwd, same convention as the CLI. This opens the *browser's* webcam (via `getUserMedia`), not the server machine's camera; works over plain `http://localhost` without HTTPS since localhost is exempt from the secure-context requirement.

There is no test suite, linter, or build step configured in this repo.

## Architecture — core eye-tracking (`src/`)

**Pipeline:** webcam frame -> MediaPipe `FaceLandmarker` (Tasks API, `VIDEO` running mode) -> per-frame face landmarks -> `gaze.compute_gaze()` -> normalized gaze coordinate -> screen mapping -> game logic. [main.py](src/main.py) contains this whole loop duplicated across three entry points, `run_calibration()`, `run_game_mode()`, and `run_blink_monitor()` — each independently opens `cv2.VideoCapture(0)` and sets up its own `FaceLandmarker`. This camera/landmarker-setup duplication is known and intentionally left alone (see "Known quirks" below); the web layer factors the shared MediaPipe setup into one place instead of touching `main.py`.

**Gaze normalization** ([gaze.py](src/gaze.py)): for each eye, `get_eye_bounds` finds the bounding box of the eye landmarks, `get_iris_center` averages the iris landmark positions (using indices from [landmarks.py](src/landmarks.py)), and `normalize_iris_position` expresses the iris center as a 0-1 fraction of the eye's bounding box. `compute_gaze(face_landmarks, smoother)` composes all of this for both eyes, averages left/right, and smooths the result through a `GazeSmoother` (exponential moving average, `alpha=0.2`) passed in by the caller — it's the single entry point both `main.py` (2 call sites) and the web `sessions/` wrappers (2 call sites) use, so the eye/iris/normalize math itself is no longer duplicated anywhere.

**Calibration** ([calibration.py](src/calibration.py)): `Calibration` walks a fixed 9-point grid (corners/edges/center of the screen), holds each point for a few seconds while the caller repeatedly calls `add_sample(gaze_x, gaze_y)`, and dumps `{version, screen: {width, height}, samples: [{screen: [x,y], gaze: [x,y]}, ...]}` to `data/calibration.json`. Point sequencing/sample windows (`0.5s`–`3.8s` sample window, advance at `4.0s`) are driven by wall-clock `time.time()`, not frame count or a fixed frame rate — this is why the web version's irregular WebSocket frame arrival doesn't break calibration timing.

**Gaze-to-screen mapping** ([gaze_region_classifier.py](src/gaze_region_classifier.py)): averages gaze samples per calibration point, sorts the 9 points by `(y, x)` to assign region numbers 1–9 topologically, and classifies live gaze by nearest-centroid. Because region numbering is purely topological (based on sort order, not absolute pixel values), the screen size used at game time doesn't need to match the screen size used at calibration time — this held up unchanged when moving to the web (calibration and game may run at different browser viewport sizes).

**Game** ([gaze_game.py](src/gaze_game.py)): `GazeGame` divides the screen into a 3x3 grid (regions 1-9, matching the classifier's region numbering), picks a random target region different from the last one, and requires the player's classified gaze region to match the target continuously for `required_gaze_time` (0.5s) to score a point and advance. Runs for a fixed `time_limit` (30s). It only tracks `score` — no accuracy or reaction-time metric exists in this class. `get_target_rect()` computes the current target's pixel rectangle from `width`/`height`; both the CLI's `draw()` (cv2 overlay) and the web's `GameSession` (sent to the browser as `state["rect"]`) call this same method, so the grid-layout math exists in exactly one place.

**Blink monitoring** ([blink_monitor.py](src/blink_monitor.py)): `BlinkMonitor.update(face_landmarks)` computes eye-aspect-ratio (EAR) per eye from fixed landmark indices, tracks open/closed transitions, and returns `{ear, left_ear, right_ear, is_blinking, blink_count}`. Pure per-frame function, no camera/UI coupling.

**Screen sizing** ([screen.py](src/screen.py)): OS-specific — uses `AppKit.NSScreen` (with `backingScaleFactor` for Retina) on macOS, `screeninfo` on Windows, and raises on anything else. **This queries the server machine's physical screen** and is only meaningful for the CLI/desktop path. The web path cannot use it — calibration/game screen dimensions there come from the browser's reported viewport size instead (see below).

**memo.py** at the repo root is a self-contained, unrelated scratch script (legacy `mp.solutions.face_mesh` API, not the Tasks API used elsewhere) implementing blink-triggered "shooting" at a target using eye-aspect-ratio blink detection. It doesn't import from or get imported by `src/`.

### Known quirks in `src/` (don't "fix" without discussion — behavior-preserving is the priority)

- `src/` modules use flat imports (`from calibration import Calibration`, etc.) — there's no package structure. Any code importing from `src/` externally (e.g. `web/backend`) must add `src/` to `sys.path` first.
- `run_calibration()`, `run_game_mode()`, `run_blink_monitor()` in `main.py` each repeat the same `FaceLandmarkerOptions` setup and camera-open/loop/cleanup boilerplate almost verbatim (the per-frame gaze math itself is *not* duplicated anymore — see `compute_gaze()` above).
- Gameplay/calibration/blink parameters (`GazeGame.time_limit=30`, `required_gaze_time=0.5`, `Calibration`'s `0.5s`/`3.8s`/`4.0s` timing window, `BlinkMonitor.threshold=0.20`) are hardcoded defaults, not constructor-exposed settings. Fine as-is for now; only worth revisiting if a settings/difficulty screen is actually planned.

**Data flow**: `Browser (getUserMedia + canvas capture) → WebSocket (binary JPEG frames) → FastAPI → src/ modules via sessions/ → JSON state → WebSocket → Browser (canvas redraw)`. HTTP is used only for serving static files — no HTTP polling anywhere in the real-time paths.

**Protocol**: for `/ws/calibration` and `/ws/game`, the client sends one JSON text message first (`{"width": ..., "height": ...}`, the browser's viewport size, replacing `screen.py`'s server-side screen query), then a stream of binary JPEG blobs. `/ws/blink` skips the init message and just streams frames. The server responds to each frame with a JSON state message; `finished: true` (or `type: "error"` for game-without-calibration) signals the client to transition screens and close the socket.

**Per-connection session model**: each WebSocket connection creates its own `FaceLandmarker` instance and its own `frame_timestamp_ms` counter (incremented by 33 per frame received, mirroring `main.py`'s fixed-step VIDEO-mode timestamping) — state lives only in memory for the connection's lifetime, nothing is shared across connections. **Calibration storage differs between CLI and web** — the CLI still reads/writes the single shared `data/calibration.json` file exactly as before (`Calibration.save(path)`/`.exists(path)`/`load_calibration_samples(path)` in `src/calibration.py`/`gaze_region_classifier.py` all take the path as a parameter, so nothing in `src/` needed to change), but the web path now stores calibration **per logged-in user in SQLite** instead: `calibration_ws.py`/`game_ws.py`/`rhythm_game_ws.py` all read `websocket.session.get("user_id")` right after `accept()` (Starlette's `SessionMiddleware` applies to the websocket ASGI scope exactly like HTTP, so this needs no extra wiring) and close the connection with a `{"type":"error"}` message if it's missing, then pass `user_id` into the session constructor. `CalibrationSession` calls `db.save_calibration(user_id, width, height, samples)` on finish; `GameSession`/`RhythmGameSession` call `db.has_calibration(user_id)` (raising `CalibrationNotFoundError` if missing, same as before) and `db.get_calibration_samples(user_id)` instead of the old `Calibration.exists()`/`load_calibration_samples()` file calls — the downstream `calculate_region_gaze()`/`create_region_points()`/`GazeRegionClassifier` in `gaze_region_classifier.py` are unchanged since they only ever operated on the in-memory samples list, indifferent to whether it came from a file or a DB row. This was a deliberate fix once multiple people (teammates) started testing the web app on a shared server — a single shared calibration file meant whoever calibrated last silently broke everyone else's game session.

**MediaPipe calls run off the shared asyncio event loop, via a dedicated single-thread `ThreadPoolExecutor` per connection** — this was a deliberate fix once team testing raised the concern that one connection's inference would block every other connection's event-loop turn (all four WS routers: `calibration_ws.py`, `game_ws.py`, `blink_ws.py`, `rhythm_game_ws.py`). Each connection creates its own `ThreadPoolExecutor(max_workers=1)` right alongside its own `FaceLandmarker` (`landmarker = await loop.run_in_executor(executor, create_landmarker)`), then routes every `detect_for_video()` call through that same executor (`await loop.run_in_executor(executor, landmarker.detect_for_video, ...)`), and tears both down together in a `finally` block (`landmarker.close()` via the executor, then `executor.shutdown(wait=False)`). **Why a dedicated single thread instead of the default shared pool** (`run_in_executor(None, ...)`): initial testing produced a false "hang" signal that looked like a GL-context thread-affinity bug — but isolated testing (calling `detect_for_video` directly, bypassing the WS layer entirely) proved calls from a background thread return in ~2ms with no hang at all; the real cause was a flawed test (a face-less synthetic frame), since every router's loop only ever calls `websocket.send_json()` after a face is detected (`if not result.face_landmarks: continue` skips silently otherwise) — a test client sending blank frames will correctly never get a reply, independent of threading. The single-dedicated-thread design was kept anyway (rather than switching to the default shared pool) since it cleanly ties the executor's lifetime to the connection's lifetime with no risk of cross-connection thread contention, and it was the version verified end-to-end (isolated direct-call test, 4 simulated concurrent connections with their own landmarker+thread each, and a real 3-connection concurrent test through the live server) — all before rolling out to routers. Rejected as a simpler alternative: moving computation to client-side JS (see `python_to_js.txt`) — that would eliminate this bottleneck even more completely (no shared server resource at all) but is a much larger structural change; this thread-pool fix is the scoped-down version appropriate for the current team-testing phase.

**All four WS routers explicitly check for a disconnect message before looping back to `receive()`**: raw `await websocket.receive()` returns `{"type": "websocket.disconnect"}` without raising on client close, and calling `receive()` again afterward raises `RuntimeError: Cannot call "receive" once a disconnect message has been received.` (not caught by `except WebSocketDisconnect`). Each router's receive loop starts with `if message["type"] == "websocket.disconnect": return` to guard against this — found and fixed in `calibration_ws.py`, `game_ws.py`, `blink_ws.py`, and `rhythm_game_ws.py` alike; no session class's algorithm logic changed, only the disconnect handling in the loop.

**Blink monitoring is scoped to the home page only** — the WebSocket connection (and thus monitoring) ends when the user navigates away from `index.html`. It's not a persistent background service that survives page navigation; making it one would need some form of state that outlives a single page's WS connection.

**Blink monitoring's capture loop runs in a dedicated Worker, not the main thread, so it survives the tab being backgrounded** — this is specific to blink monitoring (`home.js` + `camera.js`'s `startWorkerFrameSender()` + `blink_capture_worker.js`); `game.js`/`rhythm_game.js` still use the original main-thread `startFrameSender()` (`setInterval`-based) unchanged, since those require the user actively watching the screen anyway, so background survival doesn't matter for them. The motivation: Chrome throttles main-thread timers (`setInterval`/`requestAnimationFrame`) heavily once a tab becomes "hidden" — and switching to another tab and minimizing the window are the *same* hidden state at the Page Visibility API level, there's no way to distinguish them. `startWorkerFrameSender()` moves the whole capture→encode→send pipeline off the main thread: it constructs a `MediaStreamTrackProcessor` from the camera track (main thread), transfers only its `readable` stream (a transferable `ReadableStream<VideoFrame>`) into `blink_capture_worker.js`, which pulls frames, throttles them to the target fps, draws each to an `OffscreenCanvas`, JPEG-encodes it, and sends it over **its own WebSocket** opened inside the worker — the worker relays `open`/`message`/`close`/`error` events back to `home.js` via `postMessage` so the status UI updates identically either way. `MediaStreamTrackProcessor` is Chromium-only today; `startWorkerFrameSender()` feature-detects it and returns `null` on unsupported browsers (Firefox/Safari), and `home.js` falls back to the original main-thread `WebSocket` + `startFrameSender()` path unchanged in that case — so nothing breaks there, it just doesn't get the background-survival benefit. One easy-to-miss correctness detail inside the worker: every `VideoFrame` pulled from the reader must call `.close()` whether it's sent or throttle-skipped, or the browser's cap on outstanding unclosed frames silently stalls the pipeline after a couple dozen frames.

This was verified functionally with an ad-hoc Playwright script (not part of the repo — no test framework/`package.json` exists here, this ran from a throwaway scratch directory): with real Chromium and `--use-fake-device-for-media-stream`, toggling blink monitoring on `index.html` did spawn `blink_capture_worker.js` and send JPEG frames at a steady ~7fps over its own WebSocket with no stalling across a ~35s run — confirming the worker path itself works end-to-end. **What could *not* be verified this way**: whether it actually survives a genuinely backgrounded tab. Forcing a real OS-level hidden state through CDP automation (tab-switch via a second page's `bringToFront()`, and separately `Browser.setWindowBounds` reporting `windowState: "minimized"`) did not actually change `document.visibilityState`/`document.hasFocus()` in this environment — Chrome's internal state flag flipped but the real window manager never acted on it, so no genuine throttling was ever triggered to compare against. This is a sandbox/automation limitation, not evidence against the fix — the underlying claim (worker timers and a worker's own WebSocket aren't on the document's main-thread task queue, so they're outside the scope of Chrome's hidden-tab timer throttling) is standard, well-documented browser behavior. A real end-to-end confirmation should be done manually in an actual desktop Chrome window: start blink monitoring, switch to another tab (or minimize) for 20-30s, switch back, and confirm `#blink-count` kept incrementing the whole time.

**Nearby clinics (`clinics.py`/`hospitals.html`/`hospitals.js`) is unrelated to the eye-tracking pipeline** — no MediaPipe, no `src/` code, plain HTTP (not WebSocket) since it's a one-shot lookup, not a continuous stream:

- Flow: `hospitals.html` calls `navigator.geolocation.getCurrentPosition()` on load (the browser's native permission prompt is the "consent" step — no custom modal needed) → `GET /api/clinics?lat=&lng=` → renders the returned list, and separately fetches `GET /api/config` to get `naverMapClientId` and dynamically injects the Naver Maps JS SDK `<script>` tag to render markers.
- `/api/clinics` calls data.go.kr's HIRA "전국 병·의원 찾기" service (`getHsptlMdcncListInfoInqire`, `B552657/HsptlAsembySearchService`), filtered by `QD=D012` (안과's department code in this API — confirmed from the official activation guide, not guessed). That operation's response already includes `wgs84Lat`/`wgs84Lon` per institution, so straight-line distance to the browser's coordinates is computed locally with `haversine_distance_m()` — no separate geocoding or "위치정보 조회" call needed, and no reverse-geocoding step either (an earlier assumption that this API needed 시도/시군구 text turned out to be wrong once the real docs were checked).
- The service is XML-only (`response.text` parsed with stdlib `xml.etree.ElementTree`, not JSON).
- Since department data only refreshes ~daily, all ~4,255 nationwide 안과 entries are fetched once (paginated, `numOfRows=1000`, up to 10 pages) and cached in memory for `CACHE_TTL_SECONDS` (24h) in `clinics.py`'s module-level `_cache` — distance is computed per-request against the cached set, not re-fetched per request.
- If `HIRA_API_KEY` is unset, or the live call raises for any reason, `/api/clinics` silently falls back to `fetch_mock_clinics()` (a handful of synthetic clinics offset from the query point) and reports `"source": "mock"` vs `"source": "hira"` in the response — this is what lets the page work end-to-end before real keys exist.
- Only straight-line distance is shown (e.g. "350m") — walking time (the screen design mockup's "도보 5분") was explicitly decided against; not planned.
- The "눈 건강 추천 의약품" section on `hospitals.html` is an intentional empty placeholder (two static "준비 중" cards) — no data or logic behind it yet, by design.
- **Region-name search** (`GET /api/place-search?query=`, in the same `clinics.py`) lets the user type a region/address instead of relying on geolocation — implemented in three spots sharing the same logic: the home page header search bar, the home page's map-preview search box, and `hospitals.html`'s search box (originally shipped disabled/"준비 중" during the visual migration, activated later since it's the same underlying feature). It proxies to **NCP Maps' Geocoding sub-API** (`https://maps.apigw.ntruss.com/map-geocode/v2/geocode`, headers `x-ncp-apigw-api-key-id`/`x-ncp-apigw-api-key`) — the **same NCP application/account as the Maps JS SDK** (`NAVER_MAP_CLIENT_ID`), just with `NAVER_MAP_CLIENT_SECRET` added and "Geocoding" enabled for that application in the NCP console (unlike the Maps JS SDK, which only needs the Client ID). Response coordinates (`address.y`/`address.x`) are **WGS84 directly** — no coordinate-system conversion needed, unlike Naver's separate "지역 검색"(Local Search) product which was considered and rejected: that one requires a whole separate developers.naver.com/NAVER-API-HUB registration (and Naver has been mid-migration between those two consoles as of 2026, complicating new signups) *and* returns non-WGS84 coordinates. The tradeoff of using Geocoding instead: **it only resolves formal addresses/administrative region names** ("서울특별시 강남구", "강남구") — landmark or station names ("강남역", "서울시청") and business/institution names return no match. This was an explicit, deliberate scope decision (region search only, not business-name search) once the Local Search migration friction became clear. The endpoint's job is narrowly "search text → one coordinate" — everything downstream (fetching nearby clinics, rendering the list/map) reuses the existing `/api/clinics?lat=&lng=` + `js/nearby_clinics.js` code unchanged, via a shared `searchPlace(query)` helper (also in `nearby_clinics.js`) that returns the top result's `{name, address, lat, lng}`. The frontend then calls the same `initHomeMap()`/`init()` functions it already uses for geolocation results — a searched location and a geolocated location are handled identically past that point. If `NAVER_MAP_CLIENT_SECRET` is unset (or Geocoding isn't enabled for the NCP application), `/api/place-search` returns `503` and the search boxes show a "찾을 수 없습니다"-style message rather than crashing (same graceful-degradation spirit as `HIRA_API_KEY`, though there's no mock fallback for search — a missing key just means search doesn't work, not that it returns fake results). Verified working end-to-end with real coordinates (e.g. "서울특별시 강남구" → `37.517305, 127.047502`, matching Gangnam-gu's real location).

That same delta is also written to `#blink-recent-count` ("최근 1분 N회") every cycle regardless of whether it triggers an alert — a once-per-60s tumbling-window count, not a continuously-updating rolling one (a deliberate simplicity choice: it just reuses `checkBlinkRate()`'s existing cadence rather than tracking a timestamped blink history for a true sliding window). It resets to `"-"` when monitoring stops, same as `#blink-status`/`#blink-count`. That function always shows `#blink-alert` (a small warning-colored line under the blink care-item, `⚠ 최근 1분간 깜빡임이 적어요...`) for 8 seconds via a plain in-page DOM element — this part needs no permission and works whenever `index.html` is open, matching blink monitoring's existing home-page-only scope. **Login / My page (`login.html`, `mypage.html`, `js/auth.js`) — real Google OAuth + real Kakao OAuth + server session cookie**:

- **Both providers are real**, via an identical pattern: clicking "Google로 계속하기"/"카카오로 계속하기" navigates (full page load, not `fetch`) to `GET /api/auth/google/login?next=<page>` / `GET /api/auth/kakao/login?next=<page>`, which redirects to that provider's consent screen; the callback (`GET /api/auth/google/callback` / `GET /api/auth/kakao/callback`) exchanges the code, looks the user up by `google_sub` / `kakao_id`, and sets `request.session["user_id"]` — a real signed cookie (Starlette `SessionMiddleware`, see below), not a client-controlled value. Kakao's Client Secret is only sent in the token exchange if `KAKAO_CLIENT_SECRET` is set in `.env` (it's only required when "클라이언트 시크릿 > 카카오 로그인" is activated in the Kakao console — sending it when the console has it deactivated causes an `invalid_client` error, so the code only includes it conditionally). Kakao's userinfo response (`GET https://kapi.kakao.com/v2/user/me`) always has `id` but only has `kakao_account.email` if the app's email consent item is enabled and granted (email requires Kakao business-channel verification, which this project doesn't currently have set up — so Kakao-login users typically have `email = NULL`, same as any user who hasn't granted it).
- The previous Kakao **mock** login (`loginAs()` in `js/auth.js`, `POST /api/auth/login`, the `localStorage.eyeGodUserId` convenience id) was fully removed once real Kakao OAuth replaced it — there is no mock login path left in the app.
- `js/auth.js` exports `isLoggedIn()`, `getAuth()`, `logout()`, `requireLogin()`, and `syncAuthWithServer()`. `localStorage.eyeGodAuth` (`{provider, loggedInAt, userId}`) is kept only as a **fast client-side cache** for `requireLogin()`'s synchronous redirect decision — it is not the source of truth. `syncAuthWithServer()` calls `GET /api/auth/me` and rewrites that cache to match the real session; every gated page's JS (`game.js`, `rhythm_game.js`, `hospitals.js`, `analysis.js`, `mypage.js`) `await`s it before calling `requireLogin()`. This is required because both OAuth flows finish with a *server-side redirect* — the landing page's JS has no other way to learn "you're now logged in" — and it also self-heals a stale cache (e.g. an expired session) since the real API calls (`/api/mypage`, `/api/game-result`) enforce the session server-side regardless of what `localStorage` says.
- **Login policy: login is required to use any service screen** (`game.html`, `hospitals.html`, `mypage.html`, `analysis.html` all call `requireLogin()`, which redirects to `login.html?next=<page>` if not logged in; `login.js` reads `next` and carries it through as the `next` query param on whichever provider's OAuth login URL was clicked). **`index.html` is the one exception** — it never redirects, and instead shows a login prompt inline in the health-summary card when logged out.
- `mypage.html` shows, when logged in: most recent login timestamp, the most recent gaze-game score and rhythm-game score (separate cards), and a static "측정 기록 없음" placeholder for cataract risk / redness — all from `GET /api/mypage` (session-identified, see "Database" below), not `localStorage`.
- A "로그아웃" button (header + `mypage.html`) calls `logout()`, which `POST`s `/api/auth/logout` (clears the real server session) *and* clears `localStorage.eyeGodAuth`.
- **What's still out of scope**: anything past basic identity (`google_sub`/`kakao_id`, `email`) for either provider — no profile photo/name is stored or shown.

## Database (`web/backend/db.py`, SQLite)

Deliberately **stdlib `sqlite3`, no ORM/SQLAlchemy** — the query surface is a handful of single-table lookups/inserts, so an ORM would be pure overhead; `db.py` reads like `clinics.py`/`config.py` (plain functions, no classes). Each helper function opens its own `sqlite3.connect()` and closes it before returning — no shared/pooled connection — matching the project's existing "synchronous, local single-user scope" stance (see the MediaPipe note above). DB file: `data/eyegod.db`, same directory convention as `data/calibration.json`. `db.init_db()` runs once at `app.py` import time and creates tables if missing (`CREATE TABLE IF NOT EXISTS`, no migration framework, just small `_ensure_*_column()` `ALTER TABLE` checks run on every startup — fine while the schema is this small and there's one developer).

**Schema**:
- `users(id, provider, created_at, last_login_at, google_sub, email, kakao_id)` — `google_sub`/`email` are nullable (added via `_ensure_google_columns()` migration) and only ever populated for Google logins; `kakao_id` is likewise nullable (added via `_ensure_kakao_column()` migration) and only ever populated for Kakao logins. `google_sub`/`kakao_id` are how the backend recognizes a returning user for each provider — looked up via `db.get_user_by_google_sub()` / `db.get_user_by_kakao_id()` on every callback. `email` is populated by whichever provider the user logged in with last (nullable — Kakao users typically won't have one, see "Login / My page" above).
- `game_records(id, user_id, game_type, score, played_at)` — one row per finished minigame, `game_type` is `'gaze'` (S-05) or `'rhythm'` (test rhythm game, see "Rhythm minigame" below).
- `analysis_results(id, user_id, cataract_risk, redness, analyzed_at)` — **schema created but nothing writes to it yet**; reserved for when S-03 gets a real model. `GET /api/mypage` always returns `null` for these two fields today.
- `calibration_data(user_id PRIMARY KEY, data, updated_at)` — per-user calibration storage for the web path (see "Per-connection session model" above for why this replaced the old single shared `data/calibration.json` file on the web side). `data` is the same JSON shape `Calibration.save()` used to write to disk (`{version, screen:{width,height}, samples}`), stored as a TEXT blob rather than normalized into rows, since nothing queries into individual samples via SQL and the downstream `gaze_region_classifier.py` functions just want that list back as-is. `db.save_calibration()`/`has_calibration()`/`get_calibration_samples()` are the three functions (`save_calibration` upserts via the same UPDATE-then-INSERT-if-`rowcount==0` idiom as `touch_user_login()`). The CLI's `data/calibration.json` file is untouched by any of this — it's a completely separate storage path used only by `src/main.py`.

**Session cookie (`SessionMiddleware`, added in `app.py`)**: signed via `itsdangerous` (new dependency — Starlette's `SessionMiddleware` requires it), `secret_key` from `.env`'s `SESSION_SECRET_KEY` (a locally-generated random value, unrelated to either provider's credentials), `max_age` 30 days, `same_site="lax"`. **`https_only=False`** — correct only because this runs on `http://localhost` today; **this must become `True` before any real-domain deployment**, or the session cookie would be sent over plain HTTP. `request.session["user_id"]` is the one thing every protected endpoint trusts; nothing else is.

Both OAuth callbacks (`GET /api/auth/google/callback`, `GET /api/auth/kakao/callback`) set `request.session["user_id"]` the same way, so downstream endpoints don't need to know or care which provider was used — the signed session cookie is the only trust boundary for every subsequent request.

**Endpoints** (`routers/auth.py` unless noted):
- `GET /api/auth/google/login?next=` — starts the real OAuth flow: generates a CSRF `state`, stashes it (and `next`) in the session, redirects to Google's consent screen. Redirect URI is derived via `request.url_for("google_callback")`, so the app must be accessed as `http://localhost:8000` (matching what's registered in Google Cloud Console), not `127.0.0.1`.
- `GET /api/auth/google/callback` — verifies `state`, exchanges `code` for a token (`https://oauth2.googleapis.com/token`), fetches `{sub, email}` (`https://openidconnect.googleapis.com/v1/userinfo`) via `httpx.AsyncClient` (same async-client pattern as `clinics.py`), looks up/creates the user by `google_sub`, sets the session cookie, redirects to `next`.
- `GET /api/auth/kakao/login?next=` — same CSRF `state` pattern as Google, redirects to Kakao's consent screen (`https://kauth.kakao.com/oauth/authorize`). Redirect URI is derived via `request.url_for("kakao_callback")`, so the app must be accessed as `http://localhost:8000` (matching what's registered as the "카카오 로그인 리다이렉트 URI" under Kakao Developers → 내 애플리케이션 → [앱] → [플랫폼 키] → REST API 키), not `127.0.0.1`.
- `GET /api/auth/kakao/callback` — verifies `state`, exchanges `code` for a token (`https://kauth.kakao.com/oauth/token`, including `client_secret` only if `KAKAO_CLIENT_SECRET` is set), fetches `{id, kakao_account.email}` (`https://kapi.kakao.com/v2/user/me`) via `httpx.AsyncClient`, looks up/creates the user by `kakao_id`, sets the session cookie, redirects to `next`.
- `GET /api/auth/me` — `{logged_in: false}` or `{logged_in: true, user_id, provider, logged_in_at}` from the current session; this is what `js/auth.js`'s `syncAuthWithServer()` polls on every gated page load.
- `POST /api/auth/logout` — clears the session.
- `POST /api/game-result` (`routers/mypage.py`) — body is now just `{score, game_type}` (`game_type` defaults to `"gaze"`); the user comes from `Depends(get_current_user_id)` (in `auth.py`), which 401s if there's no session. Called by both `game.js`'s and `rhythm_game.js`'s `showResult()`.
- `GET /api/mypage` (`routers/mypage.py`) — same session dependency, no query params anymore; returns `{logged_in_at, last_game_gaze, last_game_rhythm, cataract_risk: null, redness: null}`. Read by `mypage.js` and the home page's health-summary card (`home.js`).

## Rhythm minigame (`rhythm_game.html`, "테스트용 미니게임")

A second minigame, built entirely on top of existing `src/` modules with **zero changes to `src/` itself** — same pattern as the S-05 gaze game (per-connection session wrapping `src/` classes, browser sends JPEG frames over WebSocket, server sends back JSON state). Linked from the home page's mini-game panel (`.game-list`, see "Home page" above) next to the real gaze-tracking game; gated by `requireLogin()` like every other service screen. A prerequisite: it reuses the same per-user calibration data as S-05 (see "Database" below), so the same logged-in account must have completed a calibration run via the S-05 game at least once first.

- **Gameplay**: 3 vertical lanes (좌/중/우); a "note" (a thin rectangle spanning the lane's width) falls down one lane at a time toward a judgment zone at the bottom. The player's gaze position moves a focus indicator between the 3 lanes (left/center/right), and a note is only catchable when it falls in the currently-focused lane. Catching is done exclusively by blinking — no click/key input. A correctly-timed catch scores points and shows "Perfect" with the note's color inverted; a mistimed or missed catch shows "Miss". ESC pauses the game with a resume/restart/quit menu (mirrors `game.html`'s existing consent-modal pattern).
- **Backend** (`web/backend/sessions/rhythm_game_session.py` + `web/backend/routers/rhythm_game_ws.py`, `/ws/rhythm-game`): server-authoritative, wall-clock (`time.time()`) timed note spawn/fall/judgment — same "not tied to camera frame rate" pattern as `Calibration`'s timing windows. Left/center/right focus is derived from `gaze_region_classifier`'s 1-9 topological regions, grouping columns (1,4,7 / 2,5,8 / 3,6,9) and picking the nearest lane to live `gaze_x`. Catch detection uses `BlinkMonitor`'s `is_blinking` **rising edge** (False→True transition) as the catch-attempt event, not the `blink_count` increment, to minimize input latency. Only one note exists on screen at a time: a single shared spawn timer picks a random lane for each new note (not one independent timer per lane). Pause/resume is a small protocol extension — the client sends `{"type": "pause"}` / `{"type": "resume"}` JSON text messages interleaved with the normal binary JPEG frame stream, and the server freezes/resumes its elapsed-time accounting accordingly.
- **Tunable constants** (top of `rhythm_game_session.py`, code constants only — no UI, by design, to leave room for a future difficulty screen): `GAME_DURATION_SEC=30`, `NOTE_FALL_DURATION_MS=3000`, `NOTE_SPAWN_MIN/MAX_INTERVAL_MS=1600/3000` (combined interval across all 3 lanes), `PERFECT_WINDOW_MS=150`, `CATCH_WINDOW_MS=400` (looser window that still counts as a non-Perfect catch attempt), `JUDGMENT_FLASH_MS=350` (how long the Perfect/Miss color flash lasts), `SCORE_PER_PERFECT=100`.
- **Frontend** (`web/frontend/rhythm_game.html` + `js/rhythm_game.js`): same webcam-consent-modal pattern as `game.html`, canvas rendering of the 3 lanes/falling notes/judgment flash/Perfect-Miss text, ESC-driven pause overlay. `showResult(score)` calls `POST /api/game-result` with `game_type: "rhythm"` (same endpoint the real gaze game uses, just tagged differently — see "Database" above), so scores do persist to the `game_records` table now; `mypage.js` shows it as its own "리듬게임 최근 점수" card, separate from the gaze game's score, and the home page's summary card does not show it (gaze-game score only).
- Discovering and fixing the WebSocket disconnect `RuntimeError` (see above) happened while building/testing this router, then was applied to the other 3 routers as well.
- A more detailed build log (original task spec, the AskUserQuestion decisions made during implementation, and a fuller mechanics writeup) lives in `rhythm_game.txt` at the repo root.
- `GAME_DURATION_SEC` is currently `30`, temporarily shortened from the spec's intended 60 seconds (1분) purely to speed up manual testing — the owner plans to set it back to the real value later, so don't "fix" it back to 60 without being asked.

## Frontend visual design (migrated from `Eye_God_New_HTML/`)

The user supplied a separate `Eye_God_New_HTML/` folder — a designer-provided visual prototype for all 6 screens (index/login/analysis/game/hospitals/mypage). That folder is **a pure UI mockup with no real functionality**: `game.html` there fakes gaze tracking with a `simulateEyeTracking()`/`setInterval` stub (no MediaPipe, no WebSocket), and every "result" is either hardcoded or randomly generated. It also has real bugs — most notably, its `index.html` checks `localStorage.eyeGodLoggedIn` while every other page checks `sessionStorage.isLoggedIn`, so login state can silently desync across tabs/restarts.

What was actually done: adopted the mockup's **design tokens and visual language** (the `:root` blue palette, Pretendard font stack, rounded 12-22px cards, header logo/eye-icon treatment, disclaimer footer) into `web/frontend/css/style.css` and each page's markup, while keeping our own existing class names/component structure rather than transplanting the mockup's CSS verbatim — the mockup's `index.html`/`game.html`/`mypage.html` each define their own bespoke, mutually-colliding class systems (e.g. three different meanings for `.header-inner`), so wholesale copying would have reintroduced that collision risk. No template engine (Jinja2) was introduced — header/footer markup is still duplicated per static HTML file exactly as it was before this migration, just now pulling shared colors/components from the one `style.css`.

The mockup's login bug was deliberately **not** carried over — `auth.js`'s single `localStorage.eyeGodAuth` object (see above) was kept as the one source of truth instead of splitting across `localStorage`/`sessionStorage`.

`clinics.html`/`clinics.js` were renamed to `hospitals.html`/`hospitals.js` to match the mockup's naming; the backend's `clinics.py` module and `/api/clinics` route were deliberately left unrenamed since renaming them would have been a pointless backend touch for a frontend-only migration.

## Data/model files

- `models/face_landmarker.task` — MediaPipe Face Landmarker model, loaded via `MODEL_PATH` in [main.py](src/main.py) and [web/backend/landmarker_factory.py](web/backend/landmarker_factory.py). Required for anything to run.
- `data/calibration.json` — **CLI-only** as of the per-user DB calibration change (see "Database" above): generated by `--calibrate` and consumed by `run_game_mode()`, `analyze_calibration.py`, and `check_json.py`. The web path (`/ws/calibration`, `/ws/game`, `/ws/rhythm-game`) no longer reads or writes this file at all — it uses the `calibration_data` SQLite table, keyed by the logged-in user's id, instead. Delete/regenerate this file if the CLI's calibration setup (monitor, camera position, screen resolution) changes; for the web path, a user just re-runs calibration and their DB row is overwritten.
