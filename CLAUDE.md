# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A webcam eye-gaze tracker built on MediaPipe Face Landmarker, being grown into a browser-based service called **Eye God** (안구 건조증 기반 백내장 위험 조기 예측 서비스). The core computer-vision logic lives in `src/` and was originally a desktop CLI app (camera opened locally, UI drawn in OpenCV windows). A FastAPI web layer in `web/` now exposes the eye-gaze minigame and blink monitoring to a browser (using the *browser user's* webcam instead of the server's), a location-based nearby eye-clinic finder that's unrelated to the camera/MediaPipe pipeline, and a login + mypage backed by a real MySQL database and server session cookie — both Google and Kakao login are real OAuth.

Not a git repository — there is no `.git` here, so there's no commit/branch history to consult.

## Environment setup

- Python 3.12.14 (pinned in `.python-version`).
- The virtualenv is `eye/` — it has all runtime deps installed (mediapipe, opencv, pyobjc for macOS screen APIs, screeninfo for Windows, fastapi, uvicorn[standard], httpx, pymysql). Activate it with `source eye/bin/activate`.
- **MySQL**: the web app requires a running MySQL server (any local instance — MySQL Workbench's bundled server, `brew install mysql`, Docker, etc. all work; this project doesn't manage the server itself) plus a database and dedicated user for it (see "Database" below for the exact `CREATE DATABASE`/`CREATE USER` statements).
- `requirements.txt` lists `pyobjc-core`/`pyobjc-framework-Cocoa`/`pyobjc-framework-Quartz` (macOS screen size in [screen.py](src/screen.py)) and `screeninfo` (Windows screen size) with `sys_platform` environment markers, so `pip install -r requirements.txt` only pulls the OS-appropriate one on each platform — both used to be missing entirely (silently relying on `eye/`'s already-installed set) until this was fixed for cross-platform testing. It also lists `python-dotenv`, which `web/backend/app.py` needs to load `.env`, and `pymysql`, which `web/backend/db.py` needs to talk to MySQL (see "Database" below).
- **`.env`** (repo root, not committed) holds secrets the web app needs: `NAVER_MAP_CLIENT_ID` (Naver Maps JS SDK, public-ish/domain-restricted identifier), `NAVER_MAP_CLIENT_SECRET` (same NCP Maps application as `NAVER_MAP_CLIENT_ID`, needed only for the server-side Geocoding calls behind the region-search boxes — the JS SDK itself never uses this), `HIRA_API_KEY` (건강보험심사평가원 병원정보 API, a real secret), `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` (Google Cloud Console OAuth client, for real Google login — see "Login / My page" below), `KAKAO_CLIENT_ID`/`KAKAO_CLIENT_SECRET` (Kakao Developers REST API key + Client Secret, for real Kakao login — `KAKAO_CLIENT_SECRET` is only required if "클라이언트 시크릿 > 카카오 로그인" is activated in the Kakao console; see "Login / My page" below), `SESSION_SECRET_KEY` (locally-generated random secret that signs the session cookie, unrelated to any external service), and `DB_HOST`/`DB_PORT`/`DB_USER`/`DB_PASSWORD`/`DB_NAME` (MySQL connection — see "Database" below). `web/backend/app.py` auto-loads it via `python-dotenv` and **requires `SESSION_SECRET_KEY` and all five `DB_*` vars to be set** (`os.environ[...]`, no defaults for user/password/name — the app won't start without them, unlike the other keys which degrade gracefully). See `.env.example` for the expected keys — copy it to `.env` and fill in real values. Missing `HIRA_API_KEY` makes the nearby-clinics feature fall back to mock data instead of failing; missing `NAVER_MAP_CLIENT_ID` just skips rendering the map (the clinic list still works); missing `NAVER_MAP_CLIENT_SECRET` makes `/api/place-search` return `503` (search boxes show a "찾을 수 없습니다" message, everything else keeps working); missing `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` or `KAKAO_CLIENT_ID` would break that provider's login buttons/callback (not currently handled gracefully — there's no mock fallback for either anymore).

## Running

All commands run from the repo root (paths like `models/face_landmarker.task` and `data/calibration.json` are relative to cwd).

### CLI / desktop mode (original, unchanged)

```bash
source eye/bin/activate

# Step 1: calibrate — shows a 3x3 grid of points on screen, one at a time,
# and records normalized iris position while you look at each. Press q to abort.
python src/main.py --calibrate

# Step 2: run the gaze-tracking game using data/calibration.json from step 1
python src/main.py

# Blink monitoring (prints to console)
python src/main.py --blink
```

Other standalone scripts (run after calibration data exists):

```bash
python src/gaze_region_classifier.py   # print the 9 calibrated region gaze-centroids
python src/analyze_calibration.py      # scatter-plot calibration samples per screen point (matplotlib)
python src/check_json.py               # print sample counts per calibration screen point
```

### Web mode (browser-based)

```bash
source eye/bin/activate
uvicorn web.backend.app:app --reload
# open http://127.0.0.1:8000 in a browser
```

Must be run from the repo root — `web/backend/app.py` resolves `models/` relative to cwd, same convention as the CLI. This opens the *browser's* webcam (via `getUserMedia`), not the server machine's camera; works over plain `http://localhost` without HTTPS since localhost is exempt from the secure-context requirement. Requires a running MySQL server reachable with the `DB_*` values in `.env` — see "Database" below.

There is no test suite, linter, or build step configured in this repo.

## Architecture — core eye-tracking (`src/`)

**Pipeline:** webcam frame -> MediaPipe `FaceLandmarker` (Tasks API, `VIDEO` running mode) -> per-frame face landmarks -> `gaze.compute_gaze()` -> normalized gaze coordinate -> screen mapping -> game logic. [main.py](src/main.py) contains this whole loop duplicated across three entry points, `run_calibration()`, `run_game_mode()`, and `run_blink_monitor()` — each independently opens `cv2.VideoCapture(0)` and sets up its own `FaceLandmarker`. This camera/landmarker-setup duplication is known and intentionally left alone (see "Known quirks" below); the web layer factors the shared MediaPipe setup into one place instead of touching `main.py`.

**Gaze normalization** ([gaze.py](src/gaze.py)): for each eye, `get_eye_bounds` finds the bounding box of the eye landmarks, `get_iris_center` averages the iris landmark positions (using indices from [landmarks.py](src/landmarks.py)), and `normalize_iris_position` expresses the iris center as a 0-1 fraction of the eye's bounding box. `compute_gaze(face_landmarks, smoother)` composes all of this for both eyes, averages left/right, and smooths the result through a `GazeSmoother` (exponential moving average, `alpha=0.2`) passed in by the caller — it's the single entry point both `main.py` (2 call sites) and the web `sessions/` wrappers (2 call sites) use, so the eye/iris/normalize math itself is no longer duplicated anywhere.

**Calibration** ([calibration.py](src/calibration.py)): `Calibration` walks a fixed 9-point grid (corners/edges/center of the screen), holds each point for a few seconds while the caller repeatedly calls `add_sample(gaze_x, gaze_y)`, and dumps `{version, screen: {width, height}, samples: [{screen: [x,y], gaze: [x,y]}, ...]}` to `data/calibration.json`. Point sequencing/sample windows (`0.5s`–`3.8s` sample window, advance at `4.0s`) are driven by wall-clock `time.time()`, not frame count or a fixed frame rate — this is why the web version's irregular WebSocket frame arrival doesn't break calibration timing.

**Gaze-to-screen mapping** ([gaze_region_classifier.py](src/gaze_region_classifier.py)): averages gaze samples per calibration point, sorts the 9 points by `(y, x)` to assign region numbers 1–9 topologically, and classifies live gaze by nearest-centroid. Because region numbering is purely topological (based on sort order, not absolute pixel values), the screen size used at game time doesn't need to match the screen size used at calibration time — this held up unchanged when moving to the web (calibration and game may run at different browser viewport sizes).

**Game** ([gaze_game.py](src/gaze_game.py)): `GazeGame` divides the screen into a 3x3 grid (regions 1-9, matching the classifier's region numbering), picks a random target region different from the last one, and requires the player's classified gaze region to match the target continuously for `required_gaze_time` (0.5s) to score a point and advance. Runs for a fixed `time_limit` (30s). It only tracks `score` — no accuracy or reaction-time metric exists in this class. `get_target_rect()` computes the current target's pixel rectangle from `width`/`height`; both the CLI's `draw()` (cv2 overlay) and the web's `GameSession` (sent to the browser as `state["rect"]`) call this same method, so the grid-layout math exists in exactly one place.

**Blink monitoring** ([blink_monitor.py](src/blink_monitor.py)): `BlinkMonitor.update(face_landmarks)` computes eye-aspect-ratio (EAR) per eye from fixed landmark indices, tracks open/closed transitions, and returns `{ear, left_ear, right_ear, is_blinking, blink_count}`. Pure per-frame function, no camera/UI coupling.

**Screen sizing** ([screen.py](src/screen.py)): OS-specific — uses `AppKit.NSScreen` (with `backingScaleFactor` for Retina) on macOS, `screeninfo` on Windows, and raises on anything else. **This queries the server machine's physical screen** and is only meaningful for the CLI/desktop path. The web path cannot use it — calibration/game screen dimensions there come from the browser's reported viewport size instead (see below).

### Known quirks in `src/` (don't "fix" without discussion — behavior-preserving is the priority)

- `src/` modules use flat imports (`from calibration import Calibration`, etc.) — there's no package structure. Any code importing from `src/` externally (e.g. `web/backend`) must add `src/` to `sys.path` first.
- `run_calibration()`, `run_game_mode()`, `run_blink_monitor()` in `main.py` each repeat the same `FaceLandmarkerOptions` setup and camera-open/loop/cleanup boilerplate almost verbatim (the per-frame gaze math itself is *not* duplicated anymore — see `compute_gaze()` above).
- Gameplay/calibration/blink parameters (`GazeGame.time_limit=30`, `required_gaze_time=0.5`, `Calibration`'s `0.5s`/`3.8s`/`4.0s` timing window, `BlinkMonitor.threshold=0.20`) are hardcoded defaults, not constructor-exposed settings. Fine as-is for now; only worth revisiting if a settings/difficulty screen is actually planned.

**Data flow**: `Browser (getUserMedia + canvas capture) → WebSocket (binary JPEG frames) → FastAPI → src/ modules via sessions/ → JSON state → WebSocket → Browser (canvas redraw)`. HTTP is used only for serving static files — no HTTP polling anywhere in the real-time paths. **This describes the two backup pages only** (`game_lab.html`, `rhythm_game_lab.html`) as of the client-side conversions below — the default minigame pages and blink monitoring now compute everything in the browser and never stream camera frames anywhere.

**Protocol**: for `/ws/calibration` and `/ws/game`, the client sends one JSON text message first (`{"width": ..., "height": ...}`, the browser's viewport size, replacing `screen.py`'s server-side screen query), then a stream of binary JPEG blobs. `/ws/blink` skips the init message and just streams frames. The server responds to each frame with a JSON state message; `finished: true` (or `type: "error"` for game-without-calibration) signals the client to transition screens and close the socket.

**Per-connection session model**: each WebSocket connection creates its own `FaceLandmarker` instance and its own `frame_timestamp_ms` counter (incremented by 33 per frame received, mirroring `main.py`'s fixed-step VIDEO-mode timestamping) — state lives only in memory for the connection's lifetime, nothing is shared across connections. **Calibration storage differs between CLI and web** — the CLI still reads/writes the single shared `data/calibration.json` file exactly as before (`Calibration.save(path)`/`.exists(path)`/`load_calibration_samples(path)` in `src/calibration.py`/`gaze_region_classifier.py` all take the path as a parameter, so nothing in `src/` needed to change), but the web path now stores calibration **per logged-in user in MySQL** instead: `calibration_ws.py`/`game_ws.py`/`rhythm_game_ws.py` (all three now backup-only — see "Gaze-tracking minigame" and "Rhythm minigame" below) all read `websocket.session.get("user_id")` right after `accept()` (Starlette's `SessionMiddleware` applies to the websocket ASGI scope exactly like HTTP, so this needs no extra wiring) and close the connection with a `{"type":"error"}` message if it's missing, then pass `user_id` into the session constructor. `CalibrationSession` calls `db.save_calibration(user_id, width, height, samples)` on finish; `GameSession`/`RhythmGameSession` call `db.has_calibration(user_id)` (raising `CalibrationNotFoundError` if missing, same as before) and `db.get_calibration_samples(user_id)` instead of the old `Calibration.exists()`/`load_calibration_samples()` file calls — the downstream `calculate_region_gaze()`/`create_region_points()`/`GazeRegionClassifier` in `gaze_region_classifier.py` are unchanged since they only ever operated on the in-memory samples list, indifferent to whether it came from a file or a DB row. This was a deliberate fix once multiple people (teammates) started testing the web app on a shared server — a single shared calibration file meant whoever calibrated last silently broke everyone else's game session.

**MediaPipe calls run off the shared asyncio event loop, via a dedicated single-thread `ThreadPoolExecutor` per connection** — this was a deliberate fix once team testing raised the concern that one connection's inference would block every other connection's event-loop turn (all four WS routers: `calibration_ws.py`, `game_ws.py`, `blink_ws.py`, `rhythm_game_ws.py`). Each connection creates its own `ThreadPoolExecutor(max_workers=1)` right alongside its own `FaceLandmarker` (`landmarker = await loop.run_in_executor(executor, create_landmarker)`), then routes every `detect_for_video()` call through that same executor (`await loop.run_in_executor(executor, landmarker.detect_for_video, ...)`), and tears both down together in a `finally` block (`landmarker.close()` via the executor, then `executor.shutdown(wait=False)`). **Why a dedicated single thread instead of the default shared pool** (`run_in_executor(None, ...)`): initial testing produced a false "hang" signal that looked like a GL-context thread-affinity bug — but isolated testing (calling `detect_for_video` directly, bypassing the WS layer entirely) proved calls from a background thread return in ~2ms with no hang at all; the real cause was a flawed test (a face-less synthetic frame), since every router's loop only ever calls `websocket.send_json()` after a face is detected (`if not result.face_landmarks: continue` skips silently otherwise) — a test client sending blank frames will correctly never get a reply, independent of threading. The single-dedicated-thread design was kept anyway (rather than switching to the default shared pool) since it cleanly ties the executor's lifetime to the connection's lifetime with no risk of cross-connection thread contention, and it was the version verified end-to-end (isolated direct-call test, 4 simulated concurrent connections with their own landmarker+thread each, and a real 3-connection concurrent test through the live server) — all before rolling out to routers. Considered as a more complete alternative at the time: moving computation to client-side JS (see `python_to_js.txt`) — that would eliminate this bottleneck even more completely (no shared server resource at all) but was judged too large a structural change for the team-testing phase this fix targeted, so the thread-pool fix shipped instead as the scoped-down version. That alternative has since been done for both minigames (`game.js` and `rhythm_game.js`, the default pages) and for blink monitoring (`home.js`, see "Home page" below) — see "Gaze-tracking minigame" and "Rhythm minigame" below. All four WS routers here still exist and still use this executor pattern, but none of them are reachable from the frontend as currently wired: `blink_ws.py` is fully dead code (no backup page calls it anymore), and `calibration_ws.py`/`game_ws.py`/`rhythm_game_ws.py` are reachable only from their respective backup pages (`game_lab.html`, `rhythm_game_lab.html`).

**All four WS routers explicitly check for a disconnect message before looping back to `receive()`**: raw `await websocket.receive()` returns `{"type": "websocket.disconnect"}` without raising on client close, and calling `receive()` again afterward raises `RuntimeError: Cannot call "receive" once a disconnect message has been received.` (not caught by `except WebSocketDisconnect`). Each router's receive loop starts with `if message["type"] == "websocket.disconnect": return` to guard against this — found and fixed in `calibration_ws.py`, `game_ws.py`, `blink_ws.py`, and `rhythm_game_ws.py` alike; no session class's algorithm logic changed, only the disconnect handling in the loop.

**Blink monitoring is scoped to the home page only** — the WebSocket connection (and thus monitoring) ends when the user navigates away from `index.html`. It's not a persistent background service that survives page navigation; making it one would need some form of state that outlives a single page's WS connection.

**Blink monitoring computes client-side now (converted 2026-09-14, same JS-conversion effort as the two minigames), and its capture loop still runs in a dedicated Worker so it survives the tab being backgrounded**:

- **Capture (worker) vs. inference (main thread) are deliberately split** — this is the one thing that makes blink monitoring's conversion different from the two minigames', and it was discovered through real browser testing, not designed upfront. The first attempt ran `FaceLandmarker` *inside* `blink_capture_worker.js` (a module worker), and it failed for both the GPU and CPU delegate with `Error: ModuleFactory not set.` Root cause (traced into the vendored `vision_bundle.mjs`): MediaPipe's WASM glue loader tries `importScripts()` first and falls back to `document.createElement("script")` — module workers have neither (`importScripts` is a classic-worker-only global; there's no `document` in any worker) — and `vision_bundle.mjs` itself can't be loaded via `importScripts()` either since it's an ES module (`export` statements aren't valid in a classic script). So today's vendored MediaPipe build cannot self-initialize inside a module worker at all, in either delegate mode. The fix: the worker only captures (pulls `VideoFrame`s from the transferred `MediaStreamTrackProcessor` readable stream, throttles to the target fps, converts each to an `ImageBitmap` via `createImageBitmap(frame, {resizeWidth, resizeHeight})`, and transfers the bitmap to the main thread via `postMessage`); `FaceLandmarker`/`BlinkMonitor` run on the main thread (`home.js`), which is the same environment `game.js`/`rhythm_game.js` already use successfully. This still preserves the background-survival goal: worker→main-thread `postMessage` delivery is not timer-based, so it isn't subject to the `setInterval`/`requestAnimationFrame` throttling Chrome applies to hidden tabs — only the *capture* needed to be off-thread, not the inference.
- `camera.js`'s `startWorkerFrameCapture(stream, options, onEvent)` (renamed from `startWorkerFrameSender` — it no longer sends anything over a network) sets up the `MediaStreamTrackProcessor` and worker exactly as before, just without the `wsUrl` it used to hand the worker. `MediaStreamTrackProcessor` is Chromium-only; on unsupported browsers (Firefox/Safari) it returns `null` and `home.js` falls back to a `game.js`-style main-thread `requestAnimationFrame` loop that reads the `<video>` element directly — same inference code path either way (`handleCapturedFrame()` for the worker path, `localVisionLoop()` for the fallback), just a different source of image frames. One easy-to-miss correctness detail inside the worker: every `VideoFrame` pulled from the reader must call `.close()` whether it's kept or throttle-skipped (and every `ImageBitmap` handed to `detectForVideo` must be `.close()`d on the main thread after use), or the browser's cap on outstanding unclosed frames silently stalls the pipeline.
- `landmarker` (the `FaceLandmarker` instance) is cached at module scope in `home.js` and reused across toggle on/off cycles within the same page load (`ensureLandmarker()`, same caching idea as `game.js`'s `prepare()`) — recreating it on every toggle would re-run WASM instantiation each time, adding a multi-second delay to what used to be a near-instant toggle. `BlinkMonitor`/the timestamp source are still recreated fresh each time monitoring starts, so `blink_count` resets to 0 per session like before.
- **What's now dead code**: `blink_ws.py`/`blink_session.py` (server-side) are no longer called by anything — unlike the two minigames, blink monitoring has no separate backup page, so there's nothing pointing at `/ws/blink` anymore. Kept as-is (harmless, small) as a reference/rollback point rather than deleted.

This was verified end-to-end with a real Playwright + Chromium run (`--use-fake-device-for-media-stream`, not part of the repo — ran from a throwaway scratch directory) against the live dev server: toggling monitoring on reached the "켜짐" status via the worker path (proving `FaceLandmarker` loads successfully on the main thread and the worker successfully delivers frames to it — this is what caught the module-worker bug above, on the *first* run before the capture/inference split existed), the low-blink-rate banner correctly appeared after the 60s window (the fake camera has no real face, so `blink_count` stays 0 the whole time, which is exactly the "too few blinks" condition — confirmed via screenshot), toggling off correctly reset all UI state, and forcing `MediaStreamTrackProcessor` to be absent (`delete window.MediaStreamTrackProcessor`) confirmed the main-thread fallback path also reaches "켜짐"/"꺼짐" correctly. The OS `Notification()` call path was also verified by spying on the constructor with `Notification.permission` forced to `"granted"` (this sandbox's Chrome-for-Testing binary always reports `"denied"` regardless of `context.grantPermissions(["notifications"])`, the same environment limitation noted below) — confirmed it's called with the correct title/body/tag exactly when permission is granted. **What still cannot be verified in this sandbox**: real OS notification popup rendering, and genuine tab-backgrounding throttling behavior (Chrome's internal visibility flag doesn't actually change under this environment's CDP automation, a pre-existing sandbox limitation predating this conversion, not something it introduced) — both need manual confirmation in a real desktop browser: start monitoring, switch to another tab (or minimize) for 20-30s, switch back, and confirm `#blink-count` kept incrementing and/or the alert popup actually appeared.

**Nearby clinics (`clinics.py`/`hospitals.html`/`hospitals.js`) is unrelated to the eye-tracking pipeline** — no MediaPipe, no `src/` code, plain HTTP (not WebSocket) since it's a one-shot lookup, not a continuous stream:

- Flow: `hospitals.html` calls `navigator.geolocation.getCurrentPosition()` on load (the browser's native permission prompt is the "consent" step — no custom modal needed) → `GET /api/clinics?lat=&lng=` → renders the returned list, and separately fetches `GET /api/config` to get `naverMapClientId` and dynamically injects the Naver Maps JS SDK `<script>` tag to render markers.
- `/api/clinics` calls data.go.kr's HIRA "전국 병·의원 찾기" service (`getHsptlMdcncListInfoInqire`, `B552657/HsptlAsembySearchService`), filtered by `QD=D012` (안과's department code in this API — confirmed from the official activation guide, not guessed). That operation's response already includes `wgs84Lat`/`wgs84Lon` per institution, so straight-line distance to the browser's coordinates is computed locally with `haversine_distance_m()` — no separate geocoding or "위치정보 조회" call needed, and no reverse-geocoding step either (an earlier assumption that this API needed 시도/시군구 text turned out to be wrong once the real docs were checked).
- The service is XML-only (`response.text` parsed with stdlib `xml.etree.ElementTree`, not JSON).
- Since department data only refreshes ~daily, all ~4,255 nationwide 안과 entries are fetched once (paginated, `numOfRows=1000`, up to 10 pages) and cached in memory for `CACHE_TTL_SECONDS` (24h) in `clinics.py`'s module-level `_cache` — distance is computed per-request against the cached set, not re-fetched per request.
- If `HIRA_API_KEY` is unset, or the live call raises for any reason, `/api/clinics` silently falls back to `fetch_mock_clinics()` (a handful of synthetic clinics offset from the query point) and reports `"source": "mock"` vs `"source": "hira"` in the response — this is what lets the page work end-to-end before real keys exist.
- Only straight-line distance is shown (e.g. "350m") — walking time (the screen design mockup's "도보 5분") was explicitly decided against; not planned.
- The "눈 건강 추천 의약품" section on `hospitals.html` is an intentional empty placeholder (two static "준비 중" cards) — no data or logic behind it yet, by design.
- **Region-name search** (`GET /api/place-search?query=`, in the same `clinics.py`) lets the user type a region/address instead of relying on geolocation — implemented in three spots sharing the same logic: the home page header search bar, the home page's map-preview search box, and `hospitals.html`'s search box (originally shipped disabled/"준비 중" during the visual migration, activated later since it's the same underlying feature). It proxies to **NCP Maps' Geocoding sub-API** (`https://maps.apigw.ntruss.com/map-geocode/v2/geocode`, headers `x-ncp-apigw-api-key-id`/`x-ncp-apigw-api-key`) — the **same NCP application/account as the Maps JS SDK** (`NAVER_MAP_CLIENT_ID`), just with `NAVER_MAP_CLIENT_SECRET` added and "Geocoding" enabled for that application in the NCP console (unlike the Maps JS SDK, which only needs the Client ID). Response coordinates (`address.y`/`address.x`) are **WGS84 directly** — no coordinate-system conversion needed, unlike Naver's separate "지역 검색"(Local Search) product which was considered and rejected: that one requires a whole separate developers.naver.com/NAVER-API-HUB registration (and Naver has been mid-migration between those two consoles as of 2026, complicating new signups) *and* returns non-WGS84 coordinates. The tradeoff of using Geocoding instead: **it only resolves formal addresses/administrative region names** ("서울특별시 강남구", "강남구") — landmark or station names ("강남역", "서울시청") and business/institution names return no match. This was an explicit, deliberate scope decision (region search only, not business-name search) once the Local Search migration friction became clear. The endpoint's job is narrowly "search text → one coordinate" — everything downstream (fetching nearby clinics, rendering the list/map) reuses the existing `/api/clinics?lat=&lng=` + `js/nearby_clinics.js` code unchanged, via a shared `searchPlace(query)` helper (also in `nearby_clinics.js`) that returns the top result's `{name, address, lat, lng}`. The frontend then calls the same `initHomeMap()`/`init()` functions it already uses for geolocation results — a searched location and a geolocated location are handled identically past that point. If `NAVER_MAP_CLIENT_SECRET` is unset (or Geocoding isn't enabled for the NCP application), `/api/place-search` returns `503` and the search boxes show a "찾을 수 없습니다"-style message rather than crashing (same graceful-degradation spirit as `HIRA_API_KEY`, though there's no mock fallback for search — a missing key just means search doesn't work, not that it returns fake results). Verified working end-to-end with real coordinates (e.g. "서울특별시 강남구" → `37.517305, 127.047502`, matching Gangnam-gu's real location).

## Database (`web/backend/db.py`, MySQL)

**Migrated from SQLite to MySQL** (via `PyMySQL`, still deliberately **no ORM/SQLAlchemy** — the query surface is a handful of single-table lookups/inserts, so an ORM would be pure overhead; `db.py` still reads like `clinics.py`/`config.py`, plain functions, no classes). Each helper function opens its own `pymysql.connect()` and closes it before returning — no shared/pooled connection — matching the project's existing "synchronous, local single-user scope" stance (see the MediaPipe note above). Connection config comes from `.env`: `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME` — all required, read via `os.environ[...]` (no defaults for user/password/name, so the app won't start without them, same strictness as `SESSION_SECRET_KEY`). `_connect()` uses `pymysql.cursors.DictCursor`, so rows come back as plain dicts already — no more `dict(row)` wrapping needed (SQLite's `sqlite3.Row` required that).

`db.init_db()` runs once at `app.py` import time and creates tables if missing (`CREATE TABLE IF NOT EXISTS`). Since this migration started the MySQL schema fresh (no pre-existing MySQL data to preserve), the old SQLite-era incremental migration functions (`_ensure_game_type_column()`, `_ensure_google_columns()`, `_ensure_kakao_column()`) were dropped entirely — every column (`google_sub`, `kakao_id`, `email`, `game_type`, etc.) is just part of the initial `CREATE TABLE` now, since there's no historical SQLite install to reconcile with. If the schema needs to change again later, a real migration tool (Alembic or hand-written `ALTER TABLE` scripts) would be worth introducing at that point — for now, editing `init_db()`'s `CREATE TABLE` statements is enough since the team can just drop and recreate the local dev database.

**Timestamps are stored as ISO8601 strings in `VARCHAR(64)` columns, not native `DATETIME`/`TIMESTAMP`** — this preserves the exact serialization `_now_iso()` already produced under SQLite (`datetime.now(timezone.utc).isoformat()`), so no date-parsing/timezone-handling code had to change anywhere (session cookies, JSON API responses, `ORDER BY played_at DESC` sorting — ISO8601 strings sort correctly as text). A deliberate choice to keep the DB-engine swap scoped to "same behavior, different storage," not a data-model redesign.

The old `data/eyegod.db` SQLite file is no longer read or written by anything — `db.py` has no notion of it anymore. It's still gitignored but otherwise just an inert leftover file; safe to delete locally.

**Local MySQL setup** (already done for this machine, documented here for reproducing elsewhere): a dedicated `eyegod` database and `eyegod_app` user (not `root`) were created on whatever local MySQL server is already running (this project doesn't install/manage the MySQL server itself — bring your own, e.g. MySQL Workbench's bundled server, `brew install mysql`, Docker, etc.):

**Schema**:
- `users(id, provider, created_at, last_login_at, google_sub, email, kakao_id)` — `google_sub`/`email` are nullable (added via `_ensure_google_columns()` migration) and only ever populated for Google logins; `kakao_id` is likewise nullable (added via `_ensure_kakao_column()` migration) and only ever populated for Kakao logins. `google_sub`/`kakao_id` are how the backend recognizes a returning user for each provider — looked up via `db.get_user_by_google_sub()` / `db.get_user_by_kakao_id()` on every callback. `email` is populated by whichever provider the user logged in with last (nullable — Kakao users typically won't have one, see "Login / My page" above).
- `game_records(game_record_id, user_id, game_type, score, played_at)` — one row per finished minigame, `game_type` is `'gaze'` (S-05) or `'rhythm'` (test rhythm game, see "Rhythm minigame" below).
- `analysis_results(analysis_id, user_id, cataract_risk, redness, analyzed_at)` — **schema created but nothing writes to it yet**; reserved for when S-03 gets a real model. `GET /api/mypage` always returns `null` for these two fields today.
- `calibration_data(user_id PRIMARY KEY, data, updated_at)` — per-user calibration storage for the web path (see "Per-connection session model" above for why this replaced the old single shared `data/calibration.json` file on the web side). `data` is the same JSON shape `Calibration.save()` used to write to disk (`{version, screen:{width,height}, samples}`), stored as a TEXT blob rather than normalized into rows, since nothing queries into individual samples via SQL and the downstream `gaze_region_classifier.py` functions just want that list back as-is. `db.save_calibration()`/`has_calibration()`/`get_calibration_samples()` are the three functions (`save_calibration` upserts via the same UPDATE-then-INSERT-if-`rowcount==0` idiom as `touch_user_login()`). The CLI's `data/calibration.json` file is untouched by any of this — it's a completely separate storage path used only by `src/main.py`.
- `blink_alerts(blink_record_id, user_id, triggered_at)` — one row per time the home page's low-blink-rate alert fires (see "Low-blink-rate alert" above), **not** a log of raw per-frame blink data. `db.log_blink_alert(user_id)` inserts a row; `home.js`'s `showBlinkAlert()` calls `POST /api/blink-alert` every time it triggers, fire-and-forget (`fetch(...).catch(() => {})`, no awaiting/error surfaced to the user) since blink monitoring works without login (`index.html` doesn't require it) and an unauthenticated call correctly 401s and is silently dropped. The intent (per explicit user request) is letting the user later judge whether they have a risky blinking habit from how often the alert fired — not building a full blink-rate time series. **Nothing reads this table back yet** — display (e.g. "이번 주 경고 N회") is deferred to whatever the mypage trend graph work below turns into.

**Session cookie (`SessionMiddleware`, added in `app.py`)**: signed via `itsdangerous` (new dependency — Starlette's `SessionMiddleware` requires it), `secret_key` from `.env`'s `SESSION_SECRET_KEY` (a locally-generated random value, unrelated to either provider's credentials), `max_age` 30 days, `same_site="lax"`. **`https_only=False`** — correct only because this runs on `http://localhost` today; **this must become `True` before any real-domain deployment**, or the session cookie would be sent over plain HTTP. `request.session["user_id"]` is the one thing every protected endpoint trusts; nothing else is.

Both OAuth callbacks (`GET /api/auth/google/callback`, `GET /api/auth/kakao/callback`) set `request.session["user_id"]` the same way, so downstream endpoints don't need to know or care which provider was used — the signed session cookie is the only trust boundary for every subsequent request.

**Endpoints** (`routers/auth.py` unless noted):
- `GET /api/auth/google/login?next=` — starts the real OAuth flow: generates a CSRF `state`, stashes it (and `next`) in the session, redirects to Google's consent screen. Redirect URI is derived via `request.url_for("google_callback")`, so the app must be accessed as `http://localhost:8000` (matching what's registered in Google Cloud Console), not `127.0.0.1`.
- `GET /api/auth/google/callback` — verifies `state`, exchanges `code` for a token (`https://oauth2.googleapis.com/token`), fetches `{sub, email}` (`https://openidconnect.googleapis.com/v1/userinfo`) via `httpx.AsyncClient` (same async-client pattern as `clinics.py`), looks up/creates the user by `google_sub`, sets the session cookie, redirects to `next`.
- `GET /api/auth/kakao/login?next=` — same CSRF `state` pattern as Google, redirects to Kakao's consent screen (`https://kauth.kakao.com/oauth/authorize`). Redirect URI is derived via `request.url_for("kakao_callback")`, so the app must be accessed as `http://localhost:8000` (matching what's registered as the "카카오 로그인 리다이렉트 URI" under Kakao Developers → 내 애플리케이션 → [앱] → [플랫폼 키] → REST API 키), not `127.0.0.1`.
- `GET /api/auth/kakao/callback` — verifies `state`, exchanges `code` for a token (`https://kauth.kakao.com/oauth/token`, including `client_secret` only if `KAKAO_CLIENT_SECRET` is set), fetches `{id, kakao_account.email}` (`https://kapi.kakao.com/v2/user/me`) via `httpx.AsyncClient`, looks up/creates the user by `kakao_id`, sets the session cookie, redirects to `next`.
- `GET /api/auth/me` — `{logged_in: false}` or `{logged_in: true, user_id, provider, logged_in_at}` from the current session; this is what `js/auth.js`'s `syncAuthWithServer()` polls on every gated page load.
- `POST /api/auth/logout` — clears the session.
- `POST /api/game-result` (`routers/mypage.py`) — body is now just `{score, game_type}` (`game_type` defaults to `"gaze"`); the user comes from `Depends(get_current_user_id)` (in `auth.py`), which 401s if there's no session. Called by `showResult()` in all four minigame entry points (`game.js`, `game_lab.js`, `rhythm_game.js`, `rhythm_game_lab.js`) — same endpoint/payload regardless of which computation path produced the score.
- `GET /api/mypage` (`routers/mypage.py`) — same session dependency, no query params anymore; returns `{logged_in_at, last_game_gaze, last_game_rhythm, cataract_risk: null, redness: null}`. Read by `mypage.js` and the home page's health-summary card (`home.js`).
- `POST /api/blink-alert` (`routers/mypage.py`) — same session dependency (401 if not logged in); no body, just records "now" for the current user into `blink_alerts`. See the `blink_alerts` schema entry above.
- `GET /api/calibration` / `POST /api/calibration` (`routers/calibration_api.py`) — both use the same session dependency. GET returns `{has_calibration, samples}` for the current user, `samples` being the same `[{"screen":[x,y],"gaze":[gx,gy]}, ...]` shape `db.get_calibration_samples()` already returned server-side; used by the rhythm minigame's `js/rhythm/calibration.js` to read an existing calibration (see "Rhythm minigame" below). POST takes `{width, height, samples}` and calls `db.save_calibration()` directly — the write-side counterpart, used by the default S-05 page's `js/game.js` once its own browser-side calibration run finishes (see "Gaze-tracking minigame" below); this is the only way a browser-computed calibration gets persisted, since `calibration_ws.py`/`calibration_session.py` (the old write path) now only run for the backup page.

## Gaze-tracking minigame (`game.html`, S-05)

Webcam consent -> calibration (9-point grid) -> 3x3 region target-catching game -> result, all one page (see "Web mode" above for the general flow). This was the second feature converted per the plan in `python_to_js.txt`, after the rhythm minigame below, and reuses several of its JS modules directly rather than re-porting them.

**Two computation paths exist side by side, same pattern as the rhythm minigame**:

- **`game.html` / `js/game.js` (default, client-side/JS computation, since 2026-09-14)**: the browser runs MediaPipe itself for both the calibration step and the game step, and never streams camera frames to a server.
  - Reuses `js/vision/faceLandmarker.js` and `js/vision/gaze.js` unchanged (already ported/verified for the rhythm minigame — see below). `js/vision/gazeRegionClassifier.js` is also reused as-is; it was originally ported *for* this game (`GazeRegionClassifier`/`calculateRegionGaze`/`createRegionPoints` mirror `gaze_region_classifier.py` exactly) even though the rhythm minigame ended up shipping first and using only the calibration-reduction half of it.
  - `js/gaze/calibrationEngine.js` is a new port of `src/calibration.py`'s `Calibration` class (9-point grid generation, `0.5s`/`3.8s`/`4.0s` sample-window timing) plus `calibration_session.py`'s per-frame driving logic. `now` is an injectable dependency (default `performance.now()/1000`, matching Python's `time.time()` units directly — unlike the rhythm engine, this one works in seconds throughout, so there's no ms↔s round-trip float error to worry about).
  - `js/gaze/gameEngine.js` is a new port of `src/gaze_game.py`'s `GazeGame` (3x3 region division, target selection with a "must differ from previous" retry loop, 0.5s dwell-time catching) plus `game_session.py`'s driving logic. `now`/`randint` are injectable the same way.
  - Both new engines follow the same dependency-injection shape as `js/rhythm/gameEngine.js`: `computeGaze`/`smoother` are passed in via `deps` rather than imported directly, so the judgment logic can be tested independently of the vision math (see "Parity testing" below).
  - Calibration finishing locally computes `regionPoints` from the just-collected samples (via `calculateRegionGaze`/`createRegionPoints`, in-memory — no server round-trip needed to start the game) and separately POSTs those samples to `/api/calibration` to persist them (`js/gaze/calibrationApi.js`) — a save failure doesn't block that play session, but leaves the DB copy stale (logged to console, not surfaced to the user; see "Database" above).
  - Matches the original's always-recalibrate-per-play behavior: every fresh play runs calibration again, same as the server-computed version always did. The retry button (after a result) re-runs only the game phase, reusing the `regionPoints` already computed this page session — same behavior the original had via re-reading the just-saved DB row, just done in memory now instead.
  - Visual design: unchanged from the original (plain canvas — white rect for the target region, score/timer text). This conversion was explicitly scoped to computation only, no redesign (unlike the rhythm minigame below).
- **`game_lab.html` / `js/game_lab.js` (backup, server-side/Python computation)**: the original architecture, byte-for-byte unchanged — browser streams JPEG frames over `/ws/calibration` then `/ws/game`, `calibration_session.py`/`game_session.py` compute and return state. Kept as a rollback path (repoint `index.html`'s minigame link to this page) exactly like `rhythm_game_lab.html`.
- **Setup requirement**: same as the rhythm minigame — `python scripts/setup_mediapipe.py` populates `web/frontend/vendor/mediapipe/`, shared by both minigames' default pages. Not needed for either backup page.
- **Parity testing** (`tests/gaze_parity/`, with a `run.sh` following the same pattern as `tests/rhythm_parity/`): `gen_expected.py` monkey-patches `calibration`/`calibration_session`/`gaze_game`/`game_session`'s module-level `time`/`random`/`db`/`compute_gaze` names (each of the four modules imports `time` into its own namespace, so all four needed patching separately — missing one was the first bug caught while writing the test, not in the ported JS). Two independent scripts: a fixed 126-frame timeline sweeping all 9 calibration points across their sample-window/advance boundaries (verified 63 samples collected, 7 per point), and an adaptive 44-frame script that reads its own engine's `current_target` each cycle to gaze at the right region (Python is ground truth — a JS target-selection bug would show up as "looking at the wrong region" and get caught by the frame-by-frame `target`/`region`/`score` diff, the same principle `tests/rhythm_parity` uses). Both passed with zero real mismatches; one single-frame `remaining`-display difference (26.3 vs 26.2) came from Python's `round()` using banker's-rounding on an exact `.x5` tie while JS's `toFixed()` doesn't — same category as the rhythm parity test's rounding note, harmless (doesn't affect `finished`), and reported separately rather than as a failure. Two real test-design bugs were caught and fixed along the way (both in the test's frame-timing construction, not the ported logic): boundary offsets landing exactly on `0.5`/`3.8`/`4.0` hit a floating-point tie that resolved differently per calibration point depending on its start time, fixed by testing just-before/just-after instead of the exact boundary; and the per-point base-time formula needed to track the *actual* offset that triggers a transition, not a nominal `4.0`, once that offset was nudged off the exact boundary. Rerun after touching any of these modules.
- `POST /api/game-result` (`{score, game_type: "gaze"}`) and `GET/POST /api/calibration` — see "Database" above; unchanged behavior from the reader's perspective regardless of which page produced the data.

## Rhythm minigame (`rhythm_game.html`, "테스트용 미니게임")

A second minigame alongside the S-05 gaze game, linked from the home page's mini-game panel (`.game-list`, see "Home page" above); gated by `requireLogin()` like every other service screen. A prerequisite: it needs the same per-user calibration data as S-05 (see "Database" below), so the same logged-in account must have completed a calibration run via the S-05 game at least once first.

- **Gameplay** (unchanged since the feature was first built): 3 vertical lanes (좌/중/우); a "note" falls down one lane at a time toward a judgment zone at the bottom. Gaze position moves a focus indicator between the 3 lanes, and a note is only catchable when it falls in the currently-focused lane. Catching is exclusively by blinking — no click/key input. A correctly-timed catch scores points and shows "Perfect"; a mistimed or missed catch shows "Miss". ESC pauses the game with a resume/restart/quit menu.

**Two computation paths exist side by side** — this was the first (and so far only) feature converted per the plan in `python_to_js.txt`:

- **`rhythm_game.html` / `js/rhythm_game.js` (default, client-side/JS computation, since 2026-09-14)**: the browser runs MediaPipe itself and never streams camera frames to a server.
  - `js/vision/faceLandmarker.js` loads MediaPipe's browser WASM build (`@mediapipe/tasks-vision`) and the same `face_landmarker.task` model the Python backend uses (GPU delegate, falls back to CPU on failure). These assets aren't in the repo — see "Setup requirement" below.
  - `js/vision/gaze.js`, `blinkMonitor.js`, `gazeRegionClassifier.js`, `landmarks.js` are direct ports of `src/gaze.py`/`blink_monitor.py`/`gaze_region_classifier.py`/`landmarks.py` — same landmark indices, same EMA alpha (0.2), same EAR threshold (0.20), same (y,x) region-sort convention for assigning region numbers 1-9.
  - `js/rhythm/gameEngine.js` is a port of `rhythm_game_session.py`'s note spawn/fall/catch/expire and scoring logic, same constants (see below). `now`/`randint`/`choice` are injectable dependencies (real implementations default to `performance.now()`/`Math.random()`) so the parity test can drive it deterministically.
  - `js/rhythm/calibration.js` calls the new `GET /api/calibration` (`routers/calibration_api.py` — the only backend change this conversion needed beyond registering it in `app.py`) and reduces the samples to the `laneX` the engine needs, the same way the Python session used to in its constructor.
  - The browser only talks to the server twice per game: once for `GET /api/calibration` before play, once for `POST /api/game-result` after — same endpoint/payload the server-computed version already used, so scoring, mypage, and `game_records` storage are identical either way.
  - **Porting risk and how it was checked**: a hand-written JS reimplementation can silently diverge from the Python original — no exception, just wrong numbers. `gazeRegionClassifier.js` in particular has two spots that fail exactly this way if done carelessly: Python's `tuple` dict key (JS arrays aren't value-comparable, so a naive port groups nothing correctly) and Python's `sorted(key=(y,x))` numeric ordering (JS's default `.sort()` compares as strings). Both were caught by deliberately reintroducing them as a negative control against `tests/vision_parity/` (see below) before trusting the port.
- **`rhythm_game_lab.html` / `js/rhythm_game_lab.js` (backup, server-side/Python computation)**: the original architecture, unchanged — browser streams JPEG frames over `/ws/rhythm-game`, `rhythm_game_session.py` computes and returns state. Kept specifically as a rollback path (repoint `index.html`'s minigame link to this page) and as a same-visuals comparison point for the client vs. server compute tradeoffs noted in `python_to_js.txt`. Also supports `?demo=1` — drives the renderer with a simulated state feed (no login/camera/calibration needed) for visual-only review, which is how the design below was iterated on before either compute path existed.
- **Visual design (neon-space, 3D perspective highway)**: built from reference screenshots under an explicit spec (mechanics untouched, visuals/effects only, no audio, must not risk the working original) — full rules, decisions, and tunables recorded in `rhythm_new.txt`. Lives in `js/rhythm/renderer.js`, a canvas-drawing module that takes a state payload (`{focus_lane, notes, score, last_judgment, remaining, finished, ...}`) and doesn't care which compute path produced it — both `rhythm_game.js` and `rhythm_game_lab.js` import the same renderer, so the two pages are pixel-identical apart from where the state comes from. Effects: perspective lanes converging to a vanishing point, hit particle bursts/shockwave rings/lane beams/screen shake, combo counter, judgment text animation, accuracy/time gauges, starfield backdrop. Theme CSS lives in `css/rhythm_game_theme.css` (`style.css` itself untouched).
- **Setup requirement**: `python scripts/setup_mediapipe.py` (repo root, stdlib only) downloads MediaPipe's WASM engine (~11MB) and a copy of the model (3.6MB) into `web/frontend/vendor/mediapipe/` — gitignored, one-time per machine, not needed at all for the backup page. Skipping it makes the default rhythm page fail at launch with a "얼굴 인식 모델을 불러오지 못했습니다" alert; see `WINDOWS_TEST_GUIDE.txt`.
- **Parity testing** (`tests/vision_parity/`, `tests/rhythm_parity/`, each with a `run.sh`): generates reference output from the real Python modules — `gen_expected.py` stubs `rhythm_game_session`'s `time`/`random`/`db`/`BlinkMonitor`/`compute_gaze` module-level names for a deterministic run rather than modifying the module itself — and diffs it frame-by-frame against the JS ports. `vision_parity` verified `compute_gaze`/EAR/blink-state-transitions/region-point assignment match to float64 precision (~1e-16), and specifically confirmed the two `gazeRegionClassifier.js` failure modes above are real and caught. `rhythm_parity` replayed 880 frames (including a pause/resume gap) through both `rhythm_game_session.py` and `gameEngine.js` and found score/perfect/miss/notes/judgments identical throughout; it also caught a real bug during development — `Math.round(x*10)/10` doesn't match Python's `round(x, 1)` (binary vs. decimal rounding) for the `remaining` display value, fixed via `toFixed`. Rerun both after touching any ported module or the constants below; safe to ignore otherwise.
- **Tunable constants now live in two places that must be kept in sync** — `rhythm_game_session.py` (backup page) and `js/rhythm/gameEngine.js` (default page): `GAME_DURATION_SEC=30`, `NOTE_FALL_DURATION_MS=3000`, `NOTE_SPAWN_MIN/MAX_INTERVAL_MS=1600/3000`, `PERFECT_WINDOW_MS=150`, `CATCH_WINDOW_MS=400`, `JUDGMENT_FLASH_MS=350`, `SCORE_PER_PERFECT=100`. The JS path detects faces at ~30fps versus the WebSocket path's ~15fps, so input latency is measurably lower on the default page today — the judgment windows haven't been retuned for that yet (known, not yet acted on; retest after any retuning with `tests/rhythm_parity/`).
- `POST /api/game-result` (`{score, game_type: "rhythm"}`) and its downstream effects — `game_records` row, `mypage.js`'s separate "리듬게임 최근 점수" card, home summary card *not* showing it (gaze-game score only) — are unchanged from the original server-computed version; see "Database" above.
- Discovering and fixing the WebSocket disconnect `RuntimeError` (see above) happened while building/testing `rhythm_game_ws.py` originally, then was applied to the other 3 routers as well — still applies to the backup page's connection.
- Build history lives across three docs: `rhythm_game.txt` (original server-computed implementation — task spec, AskUserQuestion decisions, mechanics), `rhythm_new.txt` (visual redesign — reference images, design decisions, tunables, the lab-page promotion procedure), `python_to_js.txt` (the broader client-side-computation analysis this conversion followed, written before any of it was implemented).
- `GAME_DURATION_SEC` is still `30`, temporarily shortened from the spec's intended 60 seconds purely to speed up manual testing — applies to both compute paths; don't "fix" it back to 60 without being asked.

## Frontend visual design (migrated from `Eye_God_New_HTML/`)

The user supplied a separate `Eye_God_New_HTML/` folder — a designer-provided visual prototype for all 6 screens (index/login/analysis/game/hospitals/mypage). That folder is **a pure UI mockup with no real functionality**: `game.html` there fakes gaze tracking with a `simulateEyeTracking()`/`setInterval` stub (no MediaPipe, no WebSocket), and every "result" is either hardcoded or randomly generated. It also has real bugs — most notably, its `index.html` checks `localStorage.eyeGodLoggedIn` while every other page checks `sessionStorage.isLoggedIn`, so login state can silently desync across tabs/restarts.

What was actually done: adopted the mockup's **design tokens and visual language** (the `:root` blue palette, Pretendard font stack, rounded 12-22px cards, header logo/eye-icon treatment, disclaimer footer) into `web/frontend/css/style.css` and each page's markup, while keeping our own existing class names/component structure rather than transplanting the mockup's CSS verbatim — the mockup's `index.html`/`game.html`/`mypage.html` each define their own bespoke, mutually-colliding class systems (e.g. three different meanings for `.header-inner`), so wholesale copying would have reintroduced that collision risk. No template engine (Jinja2) was introduced — header/footer markup is still duplicated per static HTML file exactly as it was before this migration, just now pulling shared colors/components from the one `style.css`.

The mockup's login bug was deliberately **not** carried over — `auth.js`'s single `localStorage.eyeGodAuth` object (see above) was kept as the one source of truth instead of splitting across `localStorage`/`sessionStorage`.

`clinics.html`/`clinics.js` were renamed to `hospitals.html`/`hospitals.js` to match the mockup's naming; the backend's `clinics.py` module and `/api/clinics` route were deliberately left unrenamed since renaming them would have been a pointless backend touch for a frontend-only migration.

All 7 pages were missing `<meta name="viewport" content="width=device-width, initial-scale=1">` until this was found and fixed — without it, mobile browsers render at a virtual desktop-width viewport (~980px) and zoom out to fit, so `style.css`'s `@media (max-width: 850px)`/`(max-width: 500px)` rules never actually trigger on a real phone even though they work correctly when narrowing a desktop browser window. Every page now has the tag (each file has no explicit `<head>`, so it's just added as a line near the top next to the existing `<title>`/`<link rel="stylesheet">`, matching how these files are already written).

At `max-width: 500px`, `header.top-bar`'s three children (`.logo`, `.header-search`, `#auth-area`) also get an explicit `order` (1/3/2) plus `.header-search { flex: 1 1 100%; }` — without this, plain `flex-wrap` breaks lines purely by available width, so exactly where the header wrapped (and thus whether the search bar ended up next to the logo, next to the login button, or alone) varied by device width instead of being consistent. Now mobile always gets logo+login on one row and the region-search bar filling its own row below, regardless of exact screen width.

`web/frontend/css/theme-healthy-lifestyle.css` exists in the repo but is **not currently linked from any page** — a test purple/lavender re-skin (built from a Figma "Healthy Lifestyle" reference image) of `index.html`'s color tokens/card shadows/quick-fab, kept as a reference in case that direction gets picked up again later. To try it, add a `<link rel="stylesheet" href="css/theme-healthy-lifestyle.css">` after `style.css`'s `<link>` in a page — it only redefines the existing `:root` custom properties plus a few card/shadow rules, so `style.css` itself never needs to change to test or drop it.

Needed for both default (client-side computation) minigame pages — `game.html` (S-05, see "Gaze-tracking minigame" above) and `rhythm_game.html` (see "Rhythm minigame" above); not needed by either backup page or anything else in the app. Re-run with `--force` to refresh after bumping `PACKAGE_VERSION` in the script.
- `data/calibration.json` — **CLI-only** as of the per-user DB calibration change (see "Database" above): generated by `--calibrate` and consumed by `run_game_mode()`, `analyze_calibration.py`, and `check_json.py`. The web path (`/ws/calibration`, `/ws/game`, `/ws/rhythm-game`) no longer reads or writes this file at all — it uses the `calibration_data` MySQL table, keyed by the logged-in user's id, instead. Delete/regenerate this file if the CLI's calibration setup (monitor, camera position, screen resolution) changes; for the web path, a user just re-runs calibration and their DB row is overwritten.
